## 设计决定（可逆，记录以便审查）

1. **不改 `opspilot/persistence.py`。** 并行任务「人工控制补全」以该文件为主战场，本任务
   的持久对象全部放在 `opspilot/web/` 各自的表中，由各自的 `install()` 建表：
   `opspilot_subject_events`（主体事件序列）、`opspilot_evidence`（raw/view/hash）、
   `opspilot_web_ledger`（intake 与 control 幂等键）。列表/查找类只读查询放在
   `DurableIncidentStore` 适配器里，写路径原样转发 `DurableStore`。
2. **事件序列是投影，不是权威。** `intake_accepted` / `control_applied` 在业务事务提交
   之后追加；崩在两者之间时 SSE 少一条事件，但页面快照来自 `rebuild()`，且游标过旧
   时发 `reload`。这是 C3 第 6 节「同一事务提交」的一个已知偏离，见「待决」。
3. **幂等身份确定性派生。** `incident_id = uuid5(key)`、`run_id = uuid5(key:run:N)`，
   确认丢失后的重试落到 `DurableStore.accept()` 的同身份幂等路径；不同内容复用 key
   由 `classify_intake_delivery` 判为 `key_conflict` → 409。
4. **结论发布沿用 `publish()` 合同：** conclusion 必须等于最终步骤的 `response`
   载荷，因此页面从 `conclusion["assistant"]["content"]` 重新 `parse_report`。
5. **追问/纠正文本** 目前只落在事件序列的 `control_applied` 载荷中，并在下一次
   `run_once` 拼进问题；`opspilot_controls` 无载荷列属并行任务范围。
6. **依赖新增** `web` 组：`fastapi==0.141.1`、`jinja2==3.1.6`、`uvicorn==0.53.0`
   （C3 第 2 节选定栈），锁定进 `uv.lock`；测试不引入 httpx/TestClient，用
   `tests/m1_web_support.py` 的最小 ASGI 驱动读 SSE 流。

## 待决（不阻塞本 PR）

- C3 第 6 节要求事件接收、主体建立、Run 创建在同一事务提交；当前 `accept()` 单事务，
  intake 幂等账本与事件序列在其后各自提交（重试幂等，但不是同一事务）。若需严格同事务，
  须由持久化任务在 `DurableStore` 增加事件/账本写入口。
- `DurableStore` 无租约续期、无 `failed/budget_exhausted` 的 run 状态写入；`run_once`
  失败路径只 `abandon()` 租约并追加 `run_handoff` 事件，run 行仍为 `running` 直到租约过期。
- 追问/纠正文本的权威落库（`opspilot_controls` 载荷列）与输入水位属并行「人工控制补全」任务。
- 同一 Run 在追问后接续被栅栏：loop 复用 `round-N` 键，重新 claim 后 `commit_tool` 落在旧代际
  步骤上得到 `CONTROL_DENIED`；PR #31 的 `begin_round` 按代际/epoch 生成键后解决。本分支
  支持的接续路径是 cancel + new_run（测试即如此）。
- close/reopen/takeover 未持久化（`DurableStore.control()` 不接受），页面不提供。
- 与并行 PR #31 的接口交汇：#31 给 `DurableStore.control()` 增加可选 `payload`，并给
  `StepCommitter` 协议增加 `begin_round` / `assert_current`。本分支的 `_EmittingCommitter`
  已预置转发这两个方法；#31 合并后应把追问/纠正文本改为经 `payload` 落入
  `opspilot_controls`，事件序列只保留投影。
