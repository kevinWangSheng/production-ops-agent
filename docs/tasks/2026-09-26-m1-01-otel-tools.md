## 决定与理由（Agent 自决，可逆；合同层项目列入简报）

1. **`TransportRequest` 增加 `tool` 字段**（执行器填 `plan.registration.name`，默认 `""` 兼容既有构造）。理由：loop 对每次调用只传一个 `bound_target_id`，一个目标一个 `source`，两个后端必须挂在同一目标下；`TransportRequest` 原本不带工具身份，transport 无法区分 metrics 与 traces 调用。这是执行器合同的加法，列入简报。
2. **一个目标 `m0-otel-20260909`，source `otel-demo`**：注册 endpoint 是 Prometheus，Jaeger 地址走 selector 的 `traces_endpoint`，两者都进目标注册表指纹并只经请求到达 transport。目标隔离靠专属实例（C3 §8「真实鉴权代理或独立实例」），不靠拼 label 过滤。
3. **观测窗由工作台在提交时固定**（`otel_demo_face(clock)`：提交时刻往前 300 秒，写进证据上下文 `policy-window-1`），worker 的执行器工厂从 Run 的输入快照读回（`scope_window`），无窗口则 `ContextError(SCOPE_WINDOW_MISSING)` → blocked；不从时钟或模型取窗口。
4. **traces 的 raw 证据是投影记录，不是 Jaeger 原始字节**：本环境 20 条 trace 的原始响应 300–600 KB、单条 ≈ 57 KB，执行器的通用逐行截断放不进任何一条；记录里带原始响应的 SHA-256 与字节数（`source_response_sha256/bytes`），投影为 M0 trace view v3 的移植（`otel-demo-traces-v1`，按请求服务→错误状态→时长采样 ≤ 20 span）。这是比 metrics（原始字节原样保存）更弱的溯源，已写进工具描述与模块文档；是否要另存原始字节属合同层取舍，列入简报。
5. **PromQL 窗口规则沿用 M0 `read_proxy`**：`offset`（大小写不敏感，全新上下文合同测试发现）、`@`、超过窗口的范围选择器、超长表达式在派发前拒绝，以 `source_status` 固定码经 `error_classes` 归为 `INVALID_PARAMS`，并带 `sent=False` 让审计记为未出站、无源接触（见审查处置 P2-1）。
6. **`DurableStore.control_state(incident_id)`**：只读快照（事故代际、状态、全局/目标挂起标志与代际），与四条写路径 `_lease_revoked` 比较的是同一批列；仍是快路径，权威栅栏不变。
7. `tool_schema_revision` 按 C3 §5 用内容哈希：模型可见 tools 数组 + 工具注册表指纹 + 投影 id；endpoint 属实例层不进哈希。
8. 实验环境脚本默认指向 M0 环境 worktree 的 `tmp/m0-environment`（pinned compose 的 bind 路径是绝对路径，专属 colima profile `m0-otel` 挂载该目录）；`development_fault.py` 只加了 `OPSPILOT_OTEL_LAB` 环境变量；健康检查用 `count(traces_span_metrics_calls_total)`（此 Prometheus 由 collector 喂数据，没有 `up`）。
