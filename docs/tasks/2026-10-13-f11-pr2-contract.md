**固定语义**

**1. 校准与首次授权**

授权不得接收新的数值 policy；所有数值取自发布记录及其冻结 profile。按指定 revision 查清单后，必须同时满足：

- 清单及条目 hash、revision、字段格式合法。
- policy 的五项目标身份等于发布快照和当前登记身份。
- profile revision／完整内容 hash 相等。
- policy `min_tracking_seconds` 等于发布记录冻结值。
- 发布的 cadence、健康窗、deadline_seconds、max_samples 等于冻结 profile。
- evaluator／mapping 为本合同支持的版本。

成功首次授权把 policy 的 revision、规范内容和 hash 写入发布主体；三者此后不可修改。恢复必须使用同一 revision，并再次通过清单检查。

**初始空清单的可断言行为**：对合法、未过期、未暂停的 pending 发布调用授权，返回 `rejected / RELEASE_POLICY_UNCALIBRATED`；追加拒绝审计；不创建 session／任务，不改变状态、代际或累计次数。不查询 Prometheus。PR-1 发布登记仍正常工作。

清单缺失或损坏返回 `RELEASE_POLICY_CATALOG_INVALID`，不能当成已校准或套默认值。已提交会话的采样、恢复读取和 replay 使用持久快照，不依赖当前文件内容；重新授权仍检查清单。

批准引用由代码／部署审查保证；数据库守卫校验快照及事务一致性，不声称能从一段 `approval_ref` 文本证明真实人工批准。

**2. 命令幂等与错误**

幂等范围为 `(observation_id, idempotency_key)`；key 长度1～256，产品调用方不能使用 `system:` 前缀。

指纹覆盖 action、actor、expected generation、policy revision。相同 key／相同指纹返回第一次的完整 receipt，只有 `replayed=True`；即使主体后来变化，也不再次执行。不同指纹抛 `IDEMPOTENCY_CONFLICT`，不改原审计。

结构非法→`INVALID_INPUT`；主体不存在→`NOT_FOUND`；这两类不写审计。数据库故障沿用 `RETRY / TIMEOUT / STORAGE_UNAVAILABLE / INTEGRITY_REFUSED`，整个事务回滚。

首次合法请求的业务拒绝写一条审计，主体不变。判定顺序固定：

1. 幂等重放／冲突。
2. `CONTROL_CONFLICT`。
3. `RELEASE_TERMINAL`。
4. 对 authorize／pause／resume：`RELEASE_DEADLINE_EXPIRED`。
5. 操作适用性：`RELEASE_PAUSED`、`ALREADY_PAUSED`、`OBSERVATION_ALREADY_AUTHORIZED`、`REAUTHORIZATION_REQUIRED`。
6. authorize／resume 的 scope：`SCOPE_SUSPENDED`。
7. 身份／profile：沿用 PR-1 拒绝码。
8. 校准：`RELEASE_POLICY_CATALOG_INVALID`、`RELEASE_POLICY_UNCALIBRATED`、`RELEASE_POLICY_MISMATCH`、`RELEASE_POLICY_UNSUPPORTED`。
9. 剩余次数为0：`RELEASE_SAMPLE_BUDGET_EXHAUSTED`。

拒绝不附带隐式到期转移；到期由清扫原语处理。

**3. 授权、暂停、恢复、取消**

- **authorize**：仅用于从未成功授权的 pending 主体。成功时 `control_generation` 不变，`observation_generation += 1`，状态变 observing；创建一个 authorized session，`authorized_at` 为锁内 DB 时间，首任务到期时间为 `authorized_at + sample_interval_seconds`。`authorization_source` 显式 NULL。
- 已经授权过但当前没有活动 session 的主体，authorize 返回 `REAUTHORIZATION_REQUIRED`，必须显式 resume。
- **pause**：active 主体且尚未 paused 才可执行。`paused=True`、控制代际和观察代际各加1；撤销活动 session，清空任务槽，ending 原因为 `authority_revoked`；发布状态保持 pending／observing。
- **resume**：允许 paused 主体，或旧会话已因 scope／绑定失效而停止的 active 主体。仍有有效活动会话且未暂停时拒绝。成功时 `paused=False`，控制代际和观察代际各加1；撤销残存旧会话，创建新 session。旧 tracking／healthy 窗口不继承。
- **cancel**：任何 active 主体可执行，包括已过 deadline 但尚未被清扫者；控制代际和观察代际各加1，状态 cancelled，`paused=False`，填写 DB `ended_at` 和 `ended_reason='cancelled'`，撤销任务。与清扫并发时先取得主体锁并提交者生效。
- 所有终态拒绝新的控制操作；同幂等键重放例外。
- 全局／目标解除挂起不自动调用 resume，不创建新会话。
- 原 deadline、max_samples、used_sample_count 永不因控制操作重置。

授权审计 `principal_kind='system'`；人工控制为 `basic_auth`。这里描述受信 Controller 调用，不在本步建立 HTTP 认证入口。

**4. 时间、覆盖与预算**

令：

```text
R = released_at
A = 当前 session.authorized_at
D = deadline_at
W = profile.evaluation_window_seconds
I = profile.session.sample_interval_seconds
H = profile.session.sustained_window_seconds
M = release.min_tracking_seconds
T = 本次查询窗口末尾，取查询开始前的 DB 时间
```

本次查询窗口固定为 `[T-W, T]`；所有查询使用同一个 Prometheus `time=T`。发布路径要求窗口长度恰为 W，且提交时 `T <= decision_at`；不使用旧恢复路径的未来窗口容差来推进发布健康结论。

- `decision_at` 为存储端持锁后取得的 DB 时间，并随采样保存；采纳要求 `decision_at < D`。
- `max(M,H) >= deadline_seconds` 一律非法；领域 policy 与 `advance_release` 同步使用严格边界。
- `T-W < A` 的数据可以保存并计入合法采样次数，但发布 verdict 为 unknown，原因 `WINDOW_BEFORE_AUTHORIZATION`，不累计任何窗口。
- 合格覆盖采样必须 `evidence_sufficient=True`。第一条将 `tracking_since=T-W`、`tracking_until=T`；后续若窗口起点不晚于此前 `tracking_until`，延长至 T，否则从当前窗口重新开始。
- 任一采纳的 unknown 清空 tracking；非采纳结果不改变水位。后续采样存在实际缺口时仍会重置。
- 健康窗沿用已批准规则：从连续合格 healthy 中第一条的**窗口末尾**起算；非 healthy 或缺口重置。
- healthy 终结同时要求：`T >= R+M`、`tracking_until-tracking_since >= M`、`T-healthy_since >= H`、`decision_at < D`。
- 一条充分证据的 degraded 采样立即 anomalous，不等待 M／H。
- 所有 release sessions 的 adopted 采样累计到主体 `used_sample_count`，包括合法 no_data／stale／timeout／failed；history_only 不计次。
- 每个 session 保留自身 `adopted_count`；新 session 保存授权时主体计数 `release_budget_used_at_authorization`。两者用于离线复核，不能把新 session 的 max_samples 当成新预算。
- 当前合格采样先判 healthy／anomalous，再判次数耗尽；未形成终态且累计达到 max_samples→unknown／`max_samples_exhausted`。
- 下一逻辑任务到期时间为本次采纳 DB 时间＋I；不补采、不中途重置发布预算。
- 重启／租约重领保持 job ID 和逻辑 sequence，仅增加 epoch。

参数校准必须计算预热窗口、查询耗时及提交后间隔；`40×60` 不能当成一小时覆盖保证。

**5. 版本切片：确定性映射**

本版适配器针对现有 checkout profile 的八个必要信号；支持阈值变化后的新 revision，但不自动接受不同信号集合、不同指标族或新 scope。四个切片信号固定为：

```text
request_rate_per_second
error_ratio
latency_p95_milliseconds
dependency_error_ratio
```

其余 Deployment／依赖状态信号只作为整体上下文。八个信号均须 required，source 必须为 prometheus。

取：

```text
N = 已登记 namespace
S = profile.subject.service = 已登记 workload
h = release.auxiliary.after_pod_template_hash
RS = S + "-" + h
```

`h` 缺失或不能构成合法 Kubernetes 名称→`VERSION_IDENTITY_MISSING`。仅配置改变、before/after images 相同的发布，还要求 before／after hash 均存在且不同；否则 `VERSION_SLICE_NOT_DISTINGUISHABLE`。

查询必须包含以下确定性关系，PromQL 空白和 matcher 顺序不构成接口：

```text
kube_replicaset_owner{
  namespace=N,replicaset=RS,
  owner_kind="Deployment",owner_name=S
}

kube_pod_owner{
  namespace=N,owner_kind="ReplicaSet",owner_name=RS
}

kube_pod_container_info{namespace=N}
  and on(namespace,pod,uid)
kube_pod_owner{
  namespace=N,owner_kind="ReplicaSet",owner_name=RS
}
```

`N/S/RS` 是转义后的精确字符串，不能拼入未经转义的 PromQL。不能以 Pod 名前缀判定归属。

每组映射保留：

- 当前值查询；
- 同一底层 selector 的 `count_over_time(...[Ws])`；
- `timestamp(...)` 新鲜度查询。

container 查询的 coverage／freshness 结果也必须通过上述精确 Pod owner 关系过滤。coverage 使用窗口内 owner 关系，不能因 Pod 已消失而静默漏掉此前实例。

映射充分的条件：

1. RS 在窗口内唯一归属 Deployment S；不能存在冲突 owner。
2. Pod UID、Pod 名、RS 关系在窗口内无冲突；窗口内出现的实例均有当前且新鲜的映射。消失或陈旧实例导致本窗 unknown，不能静默排除。
3. 每个 Pod 的容器名→image digest **完整映射**恰好等于 `after.images`；不能只比较其中一个容器，也不能忽略额外容器。
4. `image_id` 只接受 `sha256:<64hex>` 或以 `@sha256:<64hex>` 结尾的值，提取该 digest；标签、镜像 tag 不作替代。
5. `service_instance_id` 与 Pod UID 精确相等；span 的 namespace／service 和 Pod 标签若存在，必须与该映射一致。
6. 元数据覆盖下限取八个必要信号 `minimum_samples` 的最大值；freshness 取 `profile.freshness_seconds`。当前 profile 因而是3个样本、90s。
7. 单采样最多64个候选 Pod；超过上限→unknown／`VERSION_SLICE_TOO_LARGE`，不截取前64个继续判健康。

这核验的是“发布事件给出的 after 摘要集合与 hash，对应当前哪些实例”。**完整 `pod_template_digest` 仍由冻结发布事件提供；Prometheus 不重新计算配置摘要。** `service_version` 不参与版本判定；没有暴露的 Deployment／ReplicaSet UID 保留为辅助事实，不声称已由上述查询验证。

**6. 版本切片：查询与充分性**

令 U 为通过映射核验的 Pod UID 集合。对上述四个切片信号：

- 保留 profile 的 namespace、service、span_kind、span_name、status_code 条件。
- 在每个底层 span selector 增加 `service_instance_id=~"<U的精确并集>"`。
- 正则逐 UID 转义；不得空集合退化成全服务查询。
- 原 `sum/rate`、错误率分子分母、`histogram_quantile`、依赖错误率算法不变。
- 必须同时保留未切片的八个 profile 信号作为 context。

例如新版本请求量：

```text
sum(rate(traces_span_metrics_calls_total{
  k8s_namespace_name=N,service_name=S,
  span_kind="SPAN_KIND_SERVER",
  span_name=~".*CheckoutService/PlaceOrder",
  service_instance_id=~U
}[Ws]))
```

切片覆盖不能继续用跨实例 `max` 掩盖缺测：

- 对该信号底层序列使用 `min(count_over_time(...[Ws]))`。
- 另核对有覆盖记录的不同 `service_instance_id` 数量恰等于 `len(U)`；分子可能为空的 error series 不作实例存在性依据，使用对应请求／duration 底层序列。
- freshness 为匹配序列最新原始时间戳的最小值。
- 每个信号使用自己的 `minimum_samples`；健康阈值取自己的 `healthy.min/max`。
- 有效流量取切片后的 `profile.effective_traffic.signal`，要求值≥`effective_traffic.minimum`。不把整体服务流量当成新版本流量。
- 本版要求实例均有遥测覆盖，但流量门槛针对新版本集合总量；没有额外的“每 Pod 请求数”阈值。

查询键固定为：

```text
mapping:replicaset_owner:{query|coverage|freshness}
mapping:pod_owner:{query|coverage|freshness}
mapping:container_info:{query|coverage|freshness}
context:<signal_name>:{query|coverage|freshness}
after:<signal_name>:{query|coverage|freshness}
after:<signal_name>:instances
```

不能用模型生成 selector。具体执行顺序不是合同；映射不足时可以不发送 after 查询，但必须输出明确 unknown 原因。

**7. 每条发布采样的判定**

存储端从 frozen profile、policy 和 raw responses 重新计算，不接受调用方传入 `healthy`、`evidence_sufficient` 或实例集合。

充分证据要求：版本映射成立，完整授权后窗口，context 必要信号均可用，after 必要信号均可用，新版本有效流量合格。**可用不等于健康**，阈值超限仍是可用读数。

固定结果：

| 条件 | 发布采样 verdict |
|---|---|
| 充分证据，任一 after 必要信号超阈值 | degraded |
| 充分证据，context 和 after 必要信号全部健康 | healthy |
| after 健康，只有整体 context 退化 | unknown，`CONTEXT_DEGRADED_ONLY` |
| 版本、流量、覆盖、新鲜度或必要信号不足 | unknown |
| 查询失败、超时、响应不完整 | unknown |

unknown 的 `SampleOutcome` 按 `failed > timeout > stale > no_data` 取最严重者；纯版本／流量不足、context-only degradation 使用 `no_data`。这些仍可合法 adopted、计次；`SampleOutcome` 不新增 `"unknown"`。

固定证据原因码：

```text
WINDOW_BEFORE_AUTHORIZATION
VERSION_IDENTITY_MISSING
VERSION_SLICE_NOT_DISTINGUISHABLE
VERSION_MAPPING_MISSING
VERSION_MAPPING_AMBIGUOUS
VERSION_IMAGE_MISMATCH
VERSION_INSTANCE_MISMATCH
VERSION_MAPPING_STALE
VERSION_MAPPING_INSUFFICIENT_SAMPLES
VERSION_SLICE_TOO_LARGE
INSUFFICIENT_TRAFFIC
CONTEXT_DEGRADED_ONLY
HEALTH_PROFILE_UNAVAILABLE
HEALTH_PROFILE_INVALID
REQUIRED_TELEMETRY_MISSING:<scope>:<signal>
INSUFFICIENT_SAMPLES:<scope>:<signal>
STALE_TELEMETRY:<scope>:<signal>
QUERY_TIMEOUT:<query_key>
QUERY_FAILED:<query_key>
DEGRADED_SIGNAL:<scope>:<signal>
```

原因码去重、字典序排序；健康结果为空列表。若发生多项不足，全部保留。

actual query、source、evaluation time 与应有查询计划不符，属于 `readings_inconsistent`，整条 history_only；不能把越界查询伪装为合法 unknown。raw hash 错误或重复 query_key 属结构非法，提交前拒绝。

**8. 原子提交与 ending**

提交锁定 release→session 后校验：

```text
主体绑定、session/job、owner/epoch/lease、
主体与观察代际、profile/policy revision、
subject状态与paused、scope状态及scope代际、
sequence、水位、deadline、query证据一致性
```

旧恢复的 `SampleReason` 继续使用；发布同样使用 `lease_revoked`、`control_generation_stale`、`observation_generation_stale`、`subject_state_not_adoptable`、`suspended`、`deadline_expired`、`readings_inconsistent` 等既有码。

采样、原始查询、水位、主体累计次数、状态、ending、下一任务必须一个事务提交。history_only 不改主体结论、计数或窗口；确认为撤销／scope失效的 session 清空任务，不重新排期。

发布 sample_id 自身幂等：

- 同 sample_id、同 session／lease身份／窗口／查询内容返回原 receipt，`replayed=True`。
- 同 sample_id 不同内容抛 `SAMPLE_IDENTITY_CONFLICT`。
- 不同 sample_id 重交已采纳逻辑 sequence，只能 history_only。
- 原 receipt 保存于采样记录，不根据当前主体重新拼造。

release ending 固定身份：

```text
ending_id = uuid5(observation_id, "session-ending:" + str(session_id))
anomaly_key = "release-anomaly:" + str(observation_id)
```

每个 release session 至多一个 ending；每个 observation 至多一个非空 anomaly_key。ending 同时保存 job_id、job_sequence、sample_id。

| 结束原因 | session 状态 | release 转移 |
|---|---|---|
| healthy_confirmed | completed | observing→healthy |
| anomaly_detected | completed | observing→anomalous |
| deadline_expired / max_samples_exhausted | expired | active→unknown |
| authority_revoked / binding_stale / scope_suspended | revoked | 不因此终结发布主体 |
| cancelled | revoked | active→cancelled |

发布 transition 值固定为 `release_healthy / release_anomalous / release_unknown`；仅撤销和取消 session 的 ending 中 transition 为 NULL，主体取消由控制审计证明。

`pending_anomaly_endings()` 查询 anomalous 且 `incident_id IS NULL` 的唯一 ending，按 recorded_at、ending_id 排序，反复读取返回相同事实；不用可能跳过晚提交事务的高水位游标。PR-2 没有消费标记或 ack。

**9. 清扫与锁协议**

`sweep_expired_releases` 处理所有 active 且 DB now≥deadline 的发布，包括 paused、尚无 session、或旧 session 已撤销者：

- 状态→unknown，reason=`deadline_expired`，停止剩余任务。
- 有 authorized session 时追加其 ending；没有时只追加主体终结审计，不能伪造 session。
- 审计幂等键固定 `system:deadline`，actor=`observer`、principal_kind=`observer`。
- 返回本次实际终结的 observation IDs；重复清扫返回空。
- terminal 主体不再变更。

锁顺序：

- 发布采样／清扫：release→session；持锁后重读 scope，不反向取 scope 行锁。
- incident 采样保持 incident-first。
- 发布授权／人工控制：global scope→target scope→release→session。
- scope suspension：先 scope，随后按稳定 UUID 顺序锁 incidents，再锁 releases；只推进 scope generation，不重置发布计数／deadline。
- 查询前授权检查按 release 的 target_id 读取 scope；检查失败立即停止后续请求。
- PR-1 投递审计 advisory lock 保持原合同。release 控制审计不使用它，任何新路径不得持 release 锁后再请求该 advisory lock。

PR-3 将来组合登记与授权时必须在进入 PR-1 登记前取得所需 scope 锁，不能在持有投递审计锁后反向等待 scope。

**11. DB 守卫与权限**

0014 的“所有 UPDATE 一律拒绝”替换为：

- 原冻结字段始终不可改。
- 校准三列只允许首次成功授权时从全 NULL 变为完整值，此后冻结。
- terminal 不得重新进入 active；状态与 ended_at／ended_reason 一致。
- 保持发布主体和投递事件不可 DELETE／TRUNCATE；投递事件仍不可 UPDATE。

Observer 守卫：

- 只允许 observing→healthy／anomalous／unknown，以及 pending→unknown。
- healthy／anomalous 必须有**同事务**、同主体／session／代际的 adopted sample、对应 ending；健康还检查累计窗口和严格 deadline。
- unknown 必须有同事务 deadline／预算依据；无 session 的 pending 通过 deadline 审计证明。
- 不能设置 paused、代际、校准内容、incident_id，不能授权会话。
- 保留0003事故守卫原两条边，证据连接额外要求 incident purpose。

web 守卫：

- pending→observing 必须有同事务成功授权审计、新 session 和首任务。
- pause／resume／cancel 必须有匹配审计、预期代际、撤销／新会话事实。
- web 不能写 healthy／anomalous；不能调用 Observer 权限的采样提交路径。

守卫使用既有角色成员识别、固定 search_path、无 SECURITY DEFINER；拒绝 SQLSTATE **42501**，映射 `INTEGRITY_REFUSED`。证据约束延迟至事务提交检查；复用旧 sample／ending 不通过。它防代码／SQL错误，不把持有授权角色的攻击者视为无法伪造权威。

| 对象 | web | Observer | worker |
|---|---|---|---|
| release 主表 | 原权限＋UPDATE(status, paused, control_generation, observation_generation, ended_reason, ended_at, updated_at, calibrated_policy_revision, calibrated_policy_content, calibrated_policy_sha256) | SELECT；UPDATE(status, used_sample_count, ended_reason, ended_at, updated_at) | 无 |

| samples | 保持 SELECT | 原权限＋新中立判定／release结果列的 INSERT | 保持原 SELECT |
| endings | 原权限＋release绑定／中立状态／anomaly_key 的 INSERT | 同左 | 保持原 SELECT |
| release query results | SELECT | SELECT、全部业务列 INSERT | 无 |
| release audit | SELECT、全部业务列 INSERT | SELECT、全部业务列 INSERT，但只能 deadline_expired／observer 行 | 无 |

自动派生的 subject／purpose 字段不需要调用方 INSERT 权限；显式写这些字段时必须按最终实现的真实 SQL 加入精确列集，不能授整表写入。

`RUNTIME_GRANTS` 更新 web／worker 全关系矩阵；Observer 的独立权限声明和目录测试同步更新。`TRIGGER_GUARDED` 记录新增守卫。共享 observation 表原有 SELECT 意味着 worker 能读取其中新增 release 行；本步不额外收紧旧权限，也不增加 release 主表／新证据表读取权。

**12. 重放与旧证据兼容**

release replay 必须离线重新完成：raw hash校验→查询范围／时间校验→版本映射→profile阈值→采纳栅栏→窗口／累计预算→ending／状态折叠。不能把存储的 `release_evaluation` 当成判定输入。

固定完整性码：

```text
RAW_SHA256_MISMATCH
PROFILE_MISMATCH
POLICY_MISMATCH
QUERY_MISMATCH
SUBJECT_BINDING_MISMATCH
SAMPLE_DECISION_MISMATCH
WATERMARK_MISMATCH
BUDGET_MISMATCH
ENDING_MISMATCH
STATUS_MISMATCH
```

任一完整性失败：`consistent=False`、`verdict='unknown'`，同时保留重算状态供诊断；不输出已确认健康。

incident replay 继续使用原期限锚点、容差、判据和返回类型；release 使用 `released_at + deadline_seconds`，不能沿用当前 [以 session 创建时间核对期限的规则](opspilot/observer/replay.py:597)。归档缺新字段只对旧 incident 格式兼容；release 缺必需字段视为完整性失败。

```text
ReleaseStore.authorize_release_in(
```

- 授权参数读取发布记录已冻结的数值，不允许调用方覆盖 deadline、profile 或 `min_tracking_seconds`；policy revision 必须经可信清单匹配。业务拒绝返回可审计结果，存储故障整体回滚。

**风险与未确认项**

- **校准证据不足。** 现有参数来自恢复实验，记录明确说明延迟阈值不是回归检测阈值，[校准记录:35](docs/evidence/m1-02-health-profile/run.md:35)。推荐独立任务取得真实镜像／配置发布的时间线、版本映射、抓取／flush 延迟、每切片流量、健康发布／并发无关故障／不同延迟回归的检测结果，以及查询耗时、缺口和40次预算余量。按本项目约定应使用协调后的 kind 发布数据；历史可信原始数据可用于离线校准，但当前没有核对到足以冻结 U2 的发布数据。单元测试不能替代它。
- **“没有 ReplicaSet 标签”只能作有限确认。** 对归档 [observe-pre.json:24](docs/evidence/m1-02-lab/regression/normal-1/observe-pre.json:24) 的只读解析得到27组 span 标签，ReplicaSet 标签出现0次，但存在 Pod／instance 标签。配置却声明提升 ReplicaSet 属性，[values:145](scripts/kind_lab/values.yaml:145)。当前在线标签、Pod→ReplicaSet→digest 映射质量**未确认**；不能用 Pod 名前缀或固定 `service_version=2.0.2` 推导发布版本。现有 Prometheus 客户端还拒绝多序列结果，[prometheus:683](opspilot/observer/prometheus.py:683)，切片／映射查询需明确实现合同。
- **锁不仅涉及主体和 session。** PR-1 投递审计持有 advisory lock，[releases:432](opspilot/observation/releases.py:432)。组合事务和控制审计不能形成“advisory→release”与“release→advisory”反序；P2-13 分开审计可减少该风险。
- **旧 pending 不能偷偷换 policy。** PR-1 重放不更新冻结参数；若其候选值与最终校准不符，授权应拒绝并保留原因，不能原地改值或借重放重新计时。
- **尚无运行证明。** 本次未验证在线 ACL、迁移、并发事务或旧 F6 在新实现上的重放；任务记录仍写“PR-1 待合并”，与当前本地基线进展不一致，[任务记录:76](docs/tasks/2026-10-12-f11-post-release.md:76)。lead 应在裁决落档时一并更新状态。
