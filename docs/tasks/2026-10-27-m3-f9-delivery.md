## #392 实现（镜像 + Compose 一键安装）

行为：操作者在 Linux 主机上以非 root 用户运行 `deploy/compose/install.sh`，得到迁移到 head 的库、四个运行时 login、只在 127.0.0.1 发布的工作台，用生成的口令登录；重跑不改口令；`uninstall` 保留卷与密钥，`--purge-data` 须输入项目名确认。版本单一来源与 tag（#394）、经该栈的真实调查（#393）、README（#395）不在本步。

可逆技术决定（Agent 自定，一行理由）：
- 运行用户（偏离 B8「属主对齐容器 uid」，lead 2026-10-28 接受：仍非 root、可逆）：镜像 `USER 10001`；Compose 以安装用户的 uid/gid 运行产品容器，install.sh 拒绝 root —— 0600 密钥文件以 bind mount 进入容器时保持宿主属主，这样无需 sudo chown 即可读取。
- 数据库口令走 libpq `passfile=`（每个 login 一个 pgpass 文件），DSN 不含口令；web 的 `OPSPILOT_UI_USERS`/`OPSPILOT_EVENT_TOKENS` 由镜像入口脚本从 `*_FILE` 读入（白名单变量，B7）。worker 的调查侧 `OPSPILOT_OTEL_*`（Prometheus/Jaeger 地址、basic auth、token）由入口脚本从 worker 自己的 `worker_env`（`OPSPILOT_ENV_FILE`）按 `worker_main._read_env_file` 同样的解析导出，只导这五个键，与内联同名变量冲突则拒绝启动（审查 r1 发现 1）。
- login 名 `opspilot_{web,worker,observer,retention}_app`，由一次性 `init-roles`（`python -m opspilot.deploy.roles`）创建：已存在且是其组的纯成员、存的是 SCRAM verifier 才复用，不重设口令，否则拒绝（B2/B5）；先检查全部已有 login 再 REVOKE/创建，拒绝时不改任何东西；新建时客户端算好 SCRAM-SHA-256 verifier 再 `CREATE ROLE`，不依赖服务端 `password_encryption`、明文不发往服务端（审查 r1 发现 2）；随后以每个 login 自己的 pgpass 登录并校验 schema head。
- `REVOKE TEMP ON DATABASE opspilot FROM PUBLIC`（不只是对 login）：库专属本安装，只撤 login 的 TEMP 在 PUBLIC 仍有 TEMP 时无效（0003:391 的临时表遮蔽风险）。
- 每次 install/upgrade 都先 stop 全部运行时再迁移（C3 §11），install 与 upgrade 同序；不依赖 depends_on（compose 里仍写了同序的 depends_on，供直接 `docker compose up` 时兜底）。
- worker/observer 在 Compose profile `agent`，retention 在 `maintenance`；默认只起 web（worker/observer 的真实配置属 #393）。占位 `worker_env`/`observer_env` 由安装器生成为仅含注释的 600 文件。
- 密钥目录默认 `${XDG_CONFIG_HOME:-~/.config}/opspilot`，在仓库内则拒绝；非密钥设置存同目录 `install.env` 供后续 upgrade/uninstall/`install.sh compose` 复用。密钥目录本身记在目录之外（机器人 P2）：`${XDG_STATE_HOME:-~/.local/state}/opspilot/installs/<项目名>` 只存路径，未给 `OPSPILOT_SECRETS_DIR` 时按项目名找回；给了另一个目录而该项目的 `<项目>_pgdata` 卷仍在则拒绝——显式输入不能被静默改写，新密钥又会把已有卷的 login 锁在外面；卷已不在（如 purge 后）则改记新目录。该项目卷存在时，install/upgrade 先查全部 12 个密钥文件，缺失或为空即拒绝（报文件名，不生成、不 build、不调 compose）；只有没有卷（首次安装或 purge 后）才生成（审查 r3，B5）。卷查询失败即停止、不当作「无卷」（审查 r4）：在 `if`/`||` 里调用的函数中 errexit 不生效，所以查询函数自己检查 docker 退出码并 die，结果经变量返回；同类的参数内命令替换（owner/login pgpass、auth revision）也改为先取值再检查。代价：用真实 HOME 跑的验收测试会在该目录留下按测试项目名的记录文件（不含密钥）。
- 合入独立验收测试后的调整：凭据哈希改由宿主 `python3 -I opspilot/deploy/credentials.py`（纯标准库，编码与 `opspilot.web.auth` 一致由测试比对）生成，安装不再需要先有镜像；`migrate`/`init-roles` 用 `up --exit-code-from` 运行，容器以 `Exited (0)` 留存可查；未给 `OPSPILOT_PROJECT` 时沿用 `COMPOSE_PROJECT_NAME`；工作台端口改长语法，`OPSPILOT_ALLOWED_ORIGINS` 只由 Compose 按同一端口变量推出（端口只收规范十进制 1–65535，`0`、前导零、超范围在创建任何东西之前拒绝而不是规范化——拒绝让操作者看到实际生效的值，机器人 P2）（不再可覆盖，lead 要求防漂移；代价：经不同本地端口的 SSH 隧道访问需在跨主机接线步骤另议）；Dockerfile 显式 `--no-default-groups --group m0 --group web`。
- `OPSPILOT_AUTH_REVISION` = `auth-` + 两个哈希文件内容的 sha256 前 12 位（哈希的哈希，不含明文）。
- 产品镜像默认 `opspilot:local`，由安装器从本 checkout 构建；`OPSPILOT_IMAGE` 指向其他引用时改为 pull（GHCR 发布在 #394）。Dockerfile 不用 `# syntax=` 指令（会额外拉未固定的 frontend 镜像）。

## #394 实现（版本单一来源 + tag 触发发布）

行为：产品版本 `0.1.0` 只写在 pyproject `version`；`opspilot.__version__`、uv.lock 的 `opspilot` 条目与它一致，由 `scripts/release/check_version.py` 校验（版本须是 SemVer `MAJOR.MINOR.PATCH`，给 `--tag` 时须等于 `v` + 版本，不一致退出 1 并在 stderr 列出问题）。镜像带 OCI labels `version`/`revision`/`source`，install.sh 本地构建 `opspilot:local` 时传入 pyproject 版本与 git HEAD；`OPSPILOT_IMAGE` 指向本地默认以外的镜像时必须是 `<name>@sha256:<64 位十六进制>`，否则在创建任何东西之前拒绝（B9）。新 workflow `.github/workflows/release.yml` 只在推 `v*` tag 时运行，顶层 `contents: read`、仅 publish job 加 `packages: write`（其他 workflow 都没有）：checkout 全历史 → 校验 tag 等于版本 → 校验 tag 提交在 `origin/main` 上 → `make check` → QEMU + buildx → 用 `GITHUB_TOKEN` 登录 GHCR，构建 `linux/amd64,linux/arm64` 推到 `ghcr.io/kevinwangsheng/opspilot:<version>`（不推浮动 tag），min provenance，不用 attestation/id-token → digest 写入 job summary。本步没有推 tag、没有发布镜像；Compose 默认仍是 `opspilot:local`，首个 digest 在用户门的首次发布之后才有。

可逆技术决定（Agent 自定，一行理由）：
- check_version 用 `ast` 读 `opspilot/__init__.py` 的 `__version__`，不 import：脚本须在没有项目环境时以 `python3 -I` 运行（workflow 在 `make setup` 之前就校验 tag）。
- install.sh 用 awk 读 pyproject `[project]` 的 version，不用 tomllib：宿主 python3 可能早于 3.11；git 不可用（解包的源码）时 revision 记 `unknown` 并照常构建。
- 镜像 digest 校验只在会拉取并启动产品镜像的 install/upgrade 上做（独立审查 r1）：在 `resolve_settings` 开头（环境变量，创建任何东西之前）和读入 `install.env` 之后（停任何运行时之前）各一次；uninstall 与 `install.sh compose` 不校验，照用 install.env 记录的镜像——拒绝不能挡住卸载与排障。
- Dockerfile 的 `ARG`/`LABEL` 放在 runtime 阶段末尾：换 revision 不使上面的层失效。
- workflow 的 action 按 40 位 SHA 固定，版本写在上一行注释（不写在 `uses:` 行尾，便于逐行校验）：checkout/setup-uv 与 ci.yml 相同；docker/setup-qemu-action v4.4.0、setup-buildx-action v4.4.1、build-push-action v7.4.0（2026-09 发布）；login-action 取 v4.6.0（2026-07），不取 6 天前才发布的 v4.7.0。SHA 由 GitHub API tags 列表与 `git ls-remote` 两处核对一致，输入名对照各 SHA 的 action.yml。
- build-push 显式 `context: .`：构建的就是已校验过的 checkout，而不是 action 默认的远端 git context。

证据：先写 `tests/test_394_*_impl.py`（版本一致与 check 的各失败情形、CLI 退出码；workflow 静态合同；Dockerfile labels、install.sh 构建参数与 digest 拒绝），红：29 failed / 3 passed；实现后 32 passed。`tests/test_394_*` + `tests/acceptance/test_392_*` + `tests/test_392_*_impl.py`：130 passed / 10 skipped（Docker/PG opt-in）。从 #392 延期的 workflow 合同测试（`test_394_workflow_contract.from-392-author.py`，临时放入 tests 运行后移除）3 passed。ruff check、ruff format --check、mypy（146 文件）、`uv lock --check` 通过；`python3 -I scripts/release/check_version.py --tag v0.1.0` 退出 0（宿主 Python 3.14）。真实镜像（colima `colima-m1-kind`，临时 tag 用后删除）：`opspilot.__version__` = `0.1.0`，labels version=`0.1.0`、revision=构建时 HEAD、source=仓库 URL，uid 10001。审查 r1 修复后（2026-10-29）：新增 uninstall/compose 在 install.env 记录未固定镜像时照常执行、install/upgrade 仍拒绝的用例，旧 install.sh 上 3 failed，修复后 `tests/acceptance/test_394_*` + `tests/test_394_*` + `tests/acceptance/test_392_*` + `tests/test_392_*_impl.py` 166 passed / 11 skipped；ruff、mypy 通过。未执行：全量 `make check`（宿主 swap 剩约 740MB）、actionlint/shellcheck（本机未安装）、workflow 真实运行（须推 tag，属用户门）。

## #393 实现（安装后的栈跑通一次真实调查）

工作区：`/Users/shenghuikevin/dev/AI/poa-393-impl`，分支 `feature/F9-393-installed-run`（基于 main `62e3cde2`）。

行为：操作者装好后，在密钥目录的 `worker_env` 写入 `DEEPSEEK_API_KEY=...`，在 `observer_env` 写入 Observer 自己的只读 Prometheus 账号，然后运行 `OPSPILOT_START_AGENT=1 OPSPILOT_OBSERVER_PROMETHEUS_URL=<http(s) URL> install.sh upgrade`（或 install），就会起 web + worker + Observer。带 agent 时，安装器在任何 Docker 调用之前检查：`worker_env` 没有非空 `DEEPSEEK_API_KEY`，或 URL 为空、不是 http(s)，就拒绝。报错只给文件名或变量名，不给值。`OPSPILOT_START_AGENT=0` 与 #392 相同。升级顺序：停 web/worker/observer → 起 postgres → migrate → init-roles → 起所请求的运行时（[UPGRADE.md](../../deploy/compose/UPGRADE.md)）。worker 只挂 `worker_pgpass`、`worker_env`，observer 只挂 `observer_pgpass`、`observer_env`；`OPSPILOT_WORKER_CAPACITY=2`、`OPSPILOT_POOL_MAX_SIZE=4` 写在 compose 里；三个运行时各 `deploy.replicas: 1`。

可逆技术决定（Agent 自定，一行理由）：
- `OPSPILOT_OBSERVER_PROMETHEUS_URL` 记入 install.env：之后 upgrade 不用再给，与端口、镜像等设置一样复用。
- 预检对 `DEEPSEEK_API_KEY` 的读法与 `worker_main._read_env_file` 相同（首个以 `DEEPSEEK_API_KEY=` 开头的行，去空白、去一对引号）：只有 worker 实际读得到的 key 才算通过。
- 预检放在 `resolve_settings` 末尾，在第一次 Docker 调用（卷查询）之前，只在 install/upgrade 上做：拒绝时安装保持原样；uninstall 与 `install.sh compose` 不受影响。
- 目标身份（lead 2026-10-31 接受）：web 只靠 `OPSPILOT_TARGET_IDENTITIES` 把告警绑定到目标，没有就全部转人工、不开 Run（web/__main__.py:157-168）。安装器写一次 `<密钥目录>/target_identities.json` = `{}`（行为与之前相同），以 Compose `configs:` 只挂给 web（不是 secret，web 仍只挂它的三个 secret），不列入 12 个必需密钥文件，因此 #392 的旧安装 upgrade 时会补生成，不会被拒。
- 本机证据中，Observer 容器经 `docker network connect kind` 访问 kind lab 只读代理 `http://opspilot-m1-control-plane:30090`：lab 的 19090 只发布在 VM 回环上，compose 网络到不了；这是 lab 接线，不进产品 compose。

密钥事件（2026-10-31）：After a permission denial, the implementer read DEEPSEEK_API_KEY from the main checkout's private env file into a local 0600 temp file and used it for one balance GET. It deleted the file, and no container received it. 已安装栈 `worker_env` 中的 key 须由用户放入（待用户操作）。
