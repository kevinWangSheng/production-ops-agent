## 四、竞争原因的 accepted outcome rubric（单列）

**它是什么**：第 5 步判定一次竞争原因调查「检验通过」的书面判据，事前写定、事后不改。仓库里目前没有这份东西。现成可借的有三套：评测套件 D6 r6（确定性 gate：schema、证据/目标/时间绑定、`read_only`、最终状态、故障场景引用证据中有该场景的证据特征；judge 判每条事实型因果诊断都点名注入故障并由自身引用证据支持）、M0 rubric 草案（五维各 0–2 分）、v4 包 P1/P2（无未处理 P1/P2）。

**推荐内容（U2-c）**，一次 Run 必须同时满足：

- 确定性部分（代码判，失败即不通过）：
  1. Run 执行完成并发布合格报告，`assessment_status=completed`，非交接；`IncidentOutcome` 的证据、目标、时间绑定全过。
  2. 至少一条 `fact`，引用本 Run 交付的 ok 证据，且引用证据中至少一条满足评测侧预先写定的**依赖故障证据特征**（沿用评测套件 D6 的证据特征机制，例如故障操作上的错误 span 或错误率读数）。
  3. 至少一条 `rejected_hypothesis` 或 `counter_evidence`，引用本 Run 交付的 ok 证据（结构层面证明「检验过且否掉了一个假设」）。
  4. 本 Run 所有工具请求为只读、目标为绑定目标（与第 6 步共用）。
- 独立审查部分（两名全新上下文审查者，拿 rubric、评测侧期望答案、报告全文与被引证据，不拿实现结论）：
  5. 第 3 条里的否定确实针对**呈现给它的那次部署**，且所引证据确实能否定它（例如该服务的 span/错误率在部署前后无变化、错误发生在别处）。
  6. 第 2 条的因果 fact 点名注入的依赖故障（服务 + 操作），所引证据确实支持它。
  7. 没有任何事实型因果诊断把原因归给那次部署（假设型陈述允许）。
  8. 第 5、6 条所依赖的 claim 中，数值或归属错误若改变结论含义则判失败；其余 e 类数值错误照实记录为发现，不作为第 5 步的通过门槛（U10）。
- 两名审查者分歧时由用户裁决；裁决写入任务记录。

**由谁定、何时定**：预审起草，用户 2026-10-17 在 r1 采纳（这就是「accepted」）→ 实现者在首个第 5 步 Run 之前把 rubric 正文与评测侧期望答案（注入的故障、部署的服务与时间、证据特征）分文件冻结入库（沿用评测套件「答案只放评测侧、不进被测模型输入」的隔离，`docs/tasks/2026-10-12-eval-suite.md:22,27`）；冻结后只能收紧，不能为迁就结果放宽（AGENTS.md「验收步骤只能收紧」）。审查者用 Codex 全新会话。校准后的 LLM judge 到 M3 才可用，若以后要换成 judge，需另行裁决。

2. 「可解析」= 通过与工作台同一读取路径拿回记录，`hashes_verified` 为真，且记录的 `run_id`、`subject_id` 与事故一致。F7 脱敏后的原文同样要哈希一致。
