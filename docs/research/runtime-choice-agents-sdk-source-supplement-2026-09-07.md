# OpenAI Agents SDK source supplement — 2026-09-07

Fixed official source: `openai/openai-agents-python@1d471a4775bf2f40179f411824da383deb4c3fca`; manifest 0.22.0. Checkout `/tmp/opspilot-openai-agents-selection-20260907`. Read-only source/test investigation; no tests, provider requests or crash experiments ran. This narrows the ordinary Runner/session/RunState paths, not every extension.

1. **SDK already persists intermediate conversation turns, not only final reports.** Runner prepares session history through `prepare_input_with_session` before entering its loop; helper reads session.get_items with configured limit. After model/tool turn resolution, non-final non-interruption turn items are saved; session persistence helper converts items and invokes session.add_items. Conditions matter: local session persistence requires session and no server conversation tracker. Sources: [entry preparation](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/run.py#L650-L707), [history read](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/run_internal/session_persistence.py#L325-L365), [turn write caller](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/run.py#L1814-L1878), [write implementation](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/run_internal/session_persistence.py#L650-L682). Do not rank SDK lower using a claim that it lacks all intermediate persistence.

2. **Explicit RunState resumption is substantive, but distinct from conversation storage.** RunResult/streaming result expose to_state; RunState.to_json/to_string serialize execution data; Runner accepts RunState input. Streaming cancel(after_turn) finishes tool calls and session writes, then stops before next turn; consumer must keep draining events. [to_state](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/result.py#L1141-L1196), [serialization](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/run_state.py#L1776-L1818), [cancel](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/src/agents/result.py#L819-L865). Tests read: [graceful cancel](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/tests/test_soft_cancel.py#L23-L40), [resumed input after tool output](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/tests/test_run_state_pending_input.py#L136-L168) verifies prior tool executes only once and newly staged input is admitted once. These are controlled state resumption tests, not kill -9 recovery evidence.

3. **Ordinary session writes do not automatically persist the entire RunState or redispatch dead workers.** Traced write helper saves conversation items; `to_state` constructs a state and serialization returns a value to the caller. For abrupt process death, application needs a deliberate safe checkpoint/dispatch path or external durable integration; in-flight call and its uncommitted result remain an uncertainty window. This is a bounded inference from actual call paths, not a claim the whole SDK ecosystem cannot recover. Official running guide explicitly lists Dapr, Temporal, Restate and DBOS integrations: [fixed official guide](https://github.com/openai/openai-agents-python/blob/1d471a4775bf2f40179f411824da383deb4c3fca/docs/running_agents.md#L568-L584). Their execution semantics are not source-audited in this supplement, so do not assume every tool is journaled or every failure recovers exactly once. LangGraph likewise needs external worker dispatch; its distinctive built-in contribution is durable execution checkpoint boundaries, rather than an entire scheduler.

4. **Fair recommendation.** Keep SDK Python as a credible finalist. It already supplies loop, session history, interruption/continuation and serialized execution state; it is not merely an OpenAI API convenience wrapper. Compare SDK plus the actual proposed persistence/dispatcher (or one audited durable integration) against LangGraph plus its required incident service. Prefer LangGraph only if its graph checkpoint replay semantics reduce demonstrated F2 recovery work enough to offset adaptation/dependencies. Prefer SDK if native loop fits our investigation naturally and controlled continuation plus explicit durable integration meets F2 with less code. Both need incident lifecycle, evidence store, auth, target query control, late-result protection and independent recovery observation. Final choice should use identical kill-between-tool-and-save, pause/resume, pending tool, DB failure and human-cancel experiments. No runtime winner is established by this static supplement.
