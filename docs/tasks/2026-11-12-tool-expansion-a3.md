## 目标

调查能读某个 Pod 全部容器的日志，包括崩溃前上一次实例的日志。工具只进扩展档位 `otel-demo-ext`，`otel-demo` 档位不变。

## 行为（公开接口）

- `fetch_pod_logs(pod_name, namespace, start_time?, end_time?, limit?, filter?, exclude_filter?)`：取一个 Pod 全部容器的日志，当前实例与上一次实例各取一次，按时间排好，返回最新的若干行。
- 时间只收绝对时间；两端都不给时，告警 Run 用告警默认窗，否则用授权时间框结束前 1 小时。给出的时间越出授权框，或只给一端，就拒绝并回显授权框。这比上游默认 7 天窄，描述里写明。
- 默认返回 100 行，最多 1000 行；截掉了行时视图标「不完整」，并显示显示了多少、省略了多少。
- 一次读取量有上限；读满时保留已读的行、标不完整，并告诉模型读到哪个时刻、应该把起点往后移。
- 上一次实例不存在、容器还没启动：只在备注里说一句，不影响其他容器的日志。Pod 不存在：报参数错误并回显 namespace 与 Pod 名，模型可以改去列 Pod。无权读：报来源拒绝。全部为空：结果是无数据。
- `filter`、`exclude_filter` 是不区分大小写的正则，只匹配行内容；写错的正则退化为子串匹配并在备注里说明；病态正则在请求期限内被硬停，不会卡住 worker。
- 每行带时间戳、容器名、当前还是上一次实例；没有时间戳的行被丢掉并计入备注（不能证明它在授权框内）；特别长的行截断并标出。
- 描述写明它不能证明的：只含容器写到标准输出且节点仍保留的日志；没有行不证明没发生；被截或未读的行未知。

参数校验、请求方式、读取上限、计数与原因码的细节以决定表 A3-1 至 A3-11 为准。

## 这个 PR 做什么

- 在 A2 的 `kubernetes_core.py`（或同目录新模块，复用 A2 的配置与 GET 传输）里加工具与五段模型可见描述、日志流读取、正则子进程；扩展档位的数据源清单把 Pod 日志从未集成移到可用。
- 合同测试对着替身 API 响应写，由未参与实现的测试作者按本记录、决定表与 C3 编写，不看实现代码：多容器、上一次实例 400、容器未启动 400、Pod 404、403、读满、越框行、病态正则、超长行。

## 不做

日志后端（Loki 等）、持续跟随、临时调试容器、按 Deployment 取日志、快模型摘要、提示词（A7）、评测回放。

## 完成条件

## 没有真集群时的已知风险

以下未确认，到真集群上取样核对，可能返工：

1. 上一次实例不存在、容器未启动时 API 的确切状态码与 Status 体（预期 400）；A3-4 靠状态码区分。
2. 起始时间与读取字节上限同时用时 kind 的实际行为、时间戳精度。
3. otel-demo 各服务 1 小时的日志体积是否常碰 4 MiB 读取上限（决定 A3-3 的部分结果是否成为常态）。
4. 100 行日志能否放进 25,000 token 的视图（多数应能；1000 行大概率被整条拒绝，未实测）。
