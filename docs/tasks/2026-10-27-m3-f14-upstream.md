可逆技术细节（Agent 自定，一行理由）：
- Holmes 用的代理密码以 `{{ env.HOLMES_PROMETHEUS_AUTHORIZATION }}` 占位，经 `docker run -e NAME` 从调用方环境传入：配置文件里没有秘密，比 R9 的「写进只读配置」少一处落盘。
- 64k 上限只在 holmes 表单路径（审查 C 后修订）：nginx 跳到命名 location 后不再按 Content-Length 校验 `client_max_body_size`（容器实测 70k 表单得 200，只有 chunked 被拦），所以 `@holmes_form` 里另用 `$content_length` 的 map 判 >65536 返回 413，chunked 仍由该处的 `client_max_body_size 64k` 拦。其他账号保持 nginx 默认 1m，与 main 一致（70k 表单 403，2 MB 才 413）。
- POST 规则另要求 `Content-Type: application/x-www-form-urlencoded`：Holmes 的查询就是表单，收紧不影响它。
- 输出上限用 `OVERRIDE_MAX_OUTPUT_TOKEN=65536`、上下文用 `OVERRIDE_MAX_CONTENT_SIZE=1000000`：a0009195 里 `MAX_OUTPUT_TOKEN_RESERVATION` 只读不用（`holmes/common/env_vars.py:118` 无引用），U6 写的变量不生效。lead 裁定（2026-10-28 审查分诊）：这仍属 U6「只靠配置对齐」。

- Jaeger 路径白名单取 `jaeger_url` 的路径加 `/api/*`（lab 为 `/jaeger/ui/api/*`），并在 `llm_instructions` 写明基址与三个 GET 端点（配置，不是代码）。

## 隔离取证（#399，U5 清单）

做了什么（行为）：`scripts/holmes_baseline/isolation.py`。`evaluate` 是纯函数，把一次观察变成 8 项检查（缺字段即该项不过）；`probe` 在与真实 Run 完全相同的 `docker run` 形状里（同镜像、`--user 65534`、只读根、`cap-drop ALL`、`no-new-privileges`、internal 网络、两处挂载、同一组环境变量名）只替换 entrypoint 为一段 stdlib 探测脚本，探 UID、禁止路径、环境变量名（不取值）、各目标 TCP 可达性、经出口代理 CONNECT，然后读探测窗口与已记录 Run 的代理 holmes 日志。开关 `OPSPILOT_HOLMES_ISOLATION_LIVE=1`（CI 跳过）。

可逆技术细节（Agent 自定，一行理由）：
- `container.run_args` 增加可选 `entrypoint`，探测复用同一函数而不是复制参数：保证形状一致，单测比对除 entrypoint/命令外逐项相同。
- 两个秘密变量名在探测里给占位值：探测不读它们，真实凭据无需进入探测容器；名字与真实 Run 相同。
- 正向对照（审查后收紧）：同时探 `f14-lab-relay:9090/16686` 与 `f14-egress:3128` 必须可达，否则探测判无效（排除「什么都不通」被当成隔离）。
- 不可达只在失败为确定的网络层结果且同一次探测的正向对照（中继两个端口、出口代理端口、经代理 CONNECT 模型 200）全部成功时才记为 False（审查 PR #403）。确定结果：`ENETUNREACH`/`EHOSTUNREACH`（internal 网络无路由，内核立即返回）、`ECONNREFUSED`、DNS 解析失败（`gaierror`）、出口代理对 CONNECT 回 403。超时一律不算确定（可能有路由只是慢），其他异常、探测脚本无输出、对照失败同样不算；这些情况该 reach 键缺省，对应检查不过，原始错误类与 errno 记在 `observed.probe.reach_basis`。
- 实测里 DNS 失败都是 `EAI_AGAIN`（-3，internal 网络的内嵌 DNS 不转发外部查询）；每个按名字探的目标都另有按 IP 的探测（均 `ENETUNREACH`），所以名字解析失败不是单独依据。
- 探测用户 stat 失败（权限）记为「无法判定」，按「存在」计（失败即不过）；仅当同一镜像以 root、`--network none`、无挂载、`cap-drop ALL` 核对为不存在且该路径不在探测容器任何挂载下时才算不存在。首次实测 `/root/.kube` 因 `/root` 为 0700 被判「存在」，镜像核对确认不存在（`/root` 只有 `.gitconfig`）。
- 代理日志判据：GET/HEAD 只能是代理的 5 个读路径与 `label/<name>/values`，POST 只能是 `query`/`query_range`，状态不得为 403；没有任何 holmes 行也判不过。探测本身不发 holmes 请求（窗口 0 行），判据作用于已记录 Run 的 28 行。
- 模型直连目标里的 IP 由出口代理容器解析，得到的是宿主代理 DNS 的 198.18/15 假地址；直连按 IP 不通证明的是 internal 网络无路由，真实公网路由由 1.1.1.1/8.8.8.8 探测覆盖。
- worktree 的 `tmp/m1-kind-lab/kubeconfig` 临时软链到主仓库 lab kubeconfig（`KUBECONFIG` 不可配置），取证后删除。

证据（`docs/evidence/f14-holmes-baseline/isolation-probe.json`，2026-10-29T03:08Z，审查修复后重跑，kind lab 独占窗口，image ID 与 pin.json 一致）：8 项全过。UID 65534；24 个禁止路径均不存在；21 个环境变量名均在白名单（`ENV_ALLOWLIST` + 镜像自带 8 个名字）；kind API（节点名/节点 IP :6443、`10.96.0.1:443`、网关上的 API 宿主端口、中继 :6443、集群 DNS 名）、Prometheus 后端（服务名、ClusterIP、Pod IP :9090）、外网（1.1.1.1、8.8.8.8、example.com）、模型直连都不通；经出口代理 CONNECT `api.deepseek.com:443` 得 200，`example.com:443`、`1.1.1.1:443`、`api.deepseek.com:80` 得 403。附带记录：CapEff/CapPrm/CapBnd 全 0，NoNewPrivs 1，根文件系统写入被拒，挂载点只有配置文件、`/out`、`/tmp` 与运行时标准挂载。原始输出在主仓库 ignored 的 `tmp/f14-holmes/isolation-*`。
