## 六、首个实施步骤预审细节（PR-A：查询整请求上限与清理）

选它为首步：无迁移、无权限变化、不改验收步骤，且是步骤 2 断点③与步骤 3 的共同前提。

- **问题**：`OtelDemoTransport._get`（`tools/otel_demo.py:1000-1037`）把 `request.timeout_seconds` 交给 `urllib` 作 socket 超时；服务端每隔不到 30 s 送一个字节即可让 `response.read(max_bytes+1)` 持续任意长。执行器只在事后以 `elapsed > timeout` 拒收（`executor.py:1066`），期间 worker 线程被占、租约不续（续期在调用之后，`worker.py:127-141`），超过 420 s 会被另一 worker 以新 epoch 领走，原线程迟到写回成 `late_result`——安全，但工作重复且无界。
- **合同点**：
  1. 墙钟上限 = 已算好的 `timeout`（注册 30 s，剪到 Run 剩余期限，`executor.py:739,931-934`），覆盖连接、请求、读取全过程；容差：返回不晚于上限 + 1 s（线程调度与关 socket 余量）。
  2. 超时：关闭响应与底层连接、抛 `TransportTimeout`；执行器既有路径记 `timeout`/`TOOL_TIMEOUT`/`possible`（`executor.py:944-946`），审计 `sent: true`。
  3. 先到人工决定者优先：既有 `refuse_after_fetch` 顺序不变（`executor.py:998-1031`）。
  4. 收到的部分字节丢弃（R2）；本 Run 之前已提交的证据不受影响。
  5. 不加网关自动重试（U3-A）；模型看到工具错误，自行决定是否重查。
  6. 工作台工具行显示 `timeout` 与「源可能已收到请求」——现有页面是否已显示**未确认**，实现者先核对 `web/service.py` 工具状态投影。
- **不在范围**：Prometheus 以外的数据源、子进程隔离、工具并行（C3 §13 候选「工具并行 2」，现为串行，非 F2 范围）。
- **测试**（独立 Agent 按本节编写，不看实现）：本地 stdlib 慢滴 HTTP 服务器（每 5 s 一个字节、永不结束），断言：在上限 + 1 s 内得到 `timeout` 结果；调用结束后活动线程数回到基线、服务器侧连接已被关闭；连续 5 次卡住无线程泄漏；Run 已有证据 ID 不变；在途期间人工 `pause` 时结果为 `denied` 入历史而非 `timeout`；正常快速响应行为不变（回归）。
- **真实运行**：一次有界真实 Run，真实 DeepSeek、otel-demo 档、worker 的 Prometheus 地址指向宿主卡顿代理（只卡前 2 次 `query_range`，之后直通）；断言两次 `timeout` 各在 31 s 内落库、Run 继续并在报告缺口中写出该查询或按 ADR-0005 交接；附 LangSmith trace 与 `summary.json`（ADR-0006）。需 kind，排在 F11 U2 之后。
- **审查**：完成前一次全新上下文独立审查（按用户偏好走 Codex），只报违反上述合同点的缺口。
