## 目标与范围

每个观测带来源、精确查询、窗口、新鲜度、目标与可解析的证据引用；报告里事实、假设、建议、反证、被否假设可区分；缺源或源失败时报告点名缺口；参数错误、连通失败、超时、无数据四类可区分；无关近期部署加依赖故障时按冻结的 rubric 检验竞争原因；证明调查不能改动目标环境。现状差距见合同第二节：第 1、2、4 步机制已在，第 3 步缺确定性缺口展示，第 5 步缺部署可见性、场景与 rubric，第 6 步可大部分复用 F7。

不在范围：报告 schema 改版（保持 `m0-report-v2`）、新增变更历史或 K8s 工具、#95/#96/#97 的 e 类修复、`IncidentOutcome.permissions` 改为实测、LLM judge 作门。

- 前提：每个实施 PR 开工前做自己的预审（合同第七节已覆盖 PR-1）；rubric 正文与评测侧期望答案在首个第 5 步 Run 前分文件冻结入库，冻结后只能收紧。

- U2-c：rubric = 确定性 gate（完成并发布合格报告；fact 引用满足依赖故障证据特征的 ok 证据；至少一条 rejected_hypothesis 或 counter_evidence 引用 ok 证据；工具请求只读且目标正确）+ 审查只判两条因果 claim（否定该部署、点名注入的依赖故障）；其余 e 类照实记录，不设门。
- U3-a：两名全新上下文审查 Agent（Codex）判定，分歧由用户裁决；rubric 与期望答案首个 Run 前冻结。
- U4-a：第 5 步 2 次独立真实 Run 都通过；失败保留在分母，重跑一次需用户批准。
- U5-a：产品侧确定性「覆盖缺口」节，由本 Run 已提交的工具结果计算，显示在工作台与验收投影；不改提示词；#94 以被确定性展示取代关闭。

- U7-a：防循环上限强制最终轮的报告照常发布，验收投影与工作台标注「采集在上限处被截断」，不改存储。
- U8-a：Prometheus 503 且错误体 `errorType=timeout` 归 `timeout/TOOL_TIMEOUT`、`source_contact=confirmed`；其余 5xx 仍为 `SOURCE_UNAVAILABLE`；revision bump。
- U9-a：复用 F7 运行时权限证明；对 F3 验收 Run 逐条列出工具请求并断言只读与目标；在 F3 lab 时段重跑只读代理探测；`IncidentOutcome.permissions` 常量不作证据、不改；#197 照 F7 U2-a 继承。
- U10-a：e 类错误与 #95/#96/#97 不进入 F3。
- R1–R12：「观测」= 有 `EvidenceRecord` 的结果；显式 unknown 新鲜度合格；exact query = 视图字段组合；第 1 步用第 5 步 live Run 加一份归档库兼容检查；不改报告 schema；第 4 步确定性测试走真实 urllib 桩；工作台显示非 ok 的 `reason`；第 3 步回放 + 真实模型；第 5 步场景复用 F11 U2 harness；代理复测；挂到 `F3:` 场景索引；新增只读投影 `opspilot/acceptance_investigation.py`。
