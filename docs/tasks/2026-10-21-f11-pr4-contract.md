## 0. 现状要点（已核对）

- 待消费的事实已经有了：`ReleaseStore.pending_anomaly_endings(limit=20)` 只读出 `status='anomalous' AND incident_id IS NULL` 的唯一 ending（`opspilot/observation/release_commands.py:685-713`）。PR-2 有意不提供 ack（PR-2 合同:926）。
- `opspilot_release_observations.incident_id uuid REFERENCES opspilot_incidents` 列已存在（`0014_release_observations.py:76`），但目前没有角色能写它：
  - 初始守卫拒绝非空值（0014:123）。
  - 更新守卫只放行 11 个列，并拒绝 `OLD.status NOT IN ('pending','observing')`（`0015_release_observation_sessions.py:211-216`）；anomalous 是终态，所以写关联必须改守卫。
  - web 与 Observer 的 UPDATE 列表都不含 `incident_id`（0015:12-13；`opspilot/persistence/grants.py` web 段）。
- Observer 没有任何 incident 或 Run 写权限（A8、P2-03）。web 有 incidents／runs／inputs 的 INSERT，以及 incidents 的 UPDATE(state, lifecycle 等)（`grants.py` web 段）。先例：#184 的 `self_heal_pass` 在 web 进程后台线程里以 `opspilot_web` 运行，见 `opspilot/web/__main__.py:28-35,123-133,228-245` 与 C3:344。
- 事故建立原语：`_IncidentOps._accept_in(conn, …)` 在调用方事务内建事故与首个 Run（`opspilot/persistence/incidents.py:48-63`），告警接入已经这样复用（`opspilot/persistence/alerts.py:144-155`）。
- 追加事件：`append_input`（`opspilot/persistence/controls.py:627-679`）自开事务，没有 `_in(conn)` 版本。它锁事故行、按 `input_id` 幂等、`kind='event'`、调 `mark_stale_in`。模型只看到 `content` 中的 `text`、`channel`、`question` 三个字段（`opspilot/investigation/context.py:1099,1116-1138`）。
- 输入快照版本是一条线性链 v1–v5，`version` 取「最高的事实」（`context.py:58-125,516-527`）。未知的合法版本串会被判 `INCOMPATIBLE_STATE`（:551-557）。边界常量进入 `prompt_revision`（`opspilot/investigation/loop.py:114-122`）。
- 续开 Run 时重建：告警事故由 `_alert_rebuild` 从告警记录还原锚点与上下文，失败时判 `INCOMPATIBLE_STATE`（`opspilot/web/service.py:1196-1235`）。发布事故目前没有对应路径。
- 目标：发布与告警事故的 `target_id` 都指向 `opspilot_targets`（0014:54；`alerts.py:113-135`），可以按 UUID 精确匹配。交接事故的 `target_id` 为 NULL。
- 生命周期取值为 `open / observing_recovery / resolved / closed`（`0002_state_checks.py:56-61`）。领域规则是只有 closed 才建关联新事故（`domain/subjects.py:157-166`）。
- 迁移：head 是 `0017_web_suspension_grants`。0018 已分配给 F2 PR-C（`attached` 与 `related_incident_id`）。F2 B1 若加优先级列则取 0019，基于 0018（F2 合同:61,78）。
- 遥测：PR-2 的判定只采 after 窗新版本切片与整体服务 context（PR-2 合同 P2-05）。before 窗与旧实例从未查询过。web 进程没有 Prometheus 配置（`web/__main__.py` 与 `web/service.py` 中都没有相关项）。
- 校准清单仍为空（`release-calibrations.json` 为 `{"policies":[]}`），U2 policy 待用户批准写入（U2 任务记录:3）。
- 实验环境里 checkout 有告警规则 `CheckoutPlaceOrderErrorRatioHigh`（rate 5m、for 2m，`scripts/kind_lab/values.yaml:182-199`），路由到 `http://192.168.5.2:8080/intake/alertmanager`（`alertmanager-values.yaml:43`）。U2 实测从起病到 anomalous 约 4–6 分钟（`docs/evidence/f11-u2-calibration/run.md` 逐轮表）。也就是说，web 接收告警时告警事故很可能先开出来，发布异常会走「追加」而不是「新建」路径。

## 1. 九类必答

1. **时间**
   - 已定：DB 时钟；`released_at` 与 deadline 按 P1-01；采样时间按 PR-2 r8。
   - 待决：
     - before 窗起止与 old 切片的求值时刻（P4-01）。
     - 发布 Run 的授权时间框与锚点（R3）。
     - 消费等待对比采集的上限（P4-01）。
2. **计数与口径**
   - 已定：
     - 每个 observation 至多一个 `anomaly_key`（PR-2 §8）。
     - 健康、unknown 与 cancelled 都不消费：`pending_anomaly_endings` 只取 anomalous。C3「健康期不得产生无界工作」。
     - 关联已有事故时不开第二个调查（U8）。
   - 待决：
     - 每次异常最多新建 1 个事故、1 个 Run，或只追加 1 条事件（R1 幂等键）。
     - 对比采集的查询数上限（P4-01）。
3. **状态转移**
   - 已定：
     - 发布状态停在 anomalous，不再变。
     - 已关闭事故按新异常规则新建关联事故（A6、C3:105）。
     - 追加的事件不推进分析水位（F2 合同:34）。
   - 待决：
     - 「开放」判据与多个候选时选哪一个（P4-04）。
     - 目标无法解析时的去向（R7）。
     - 消费由谁、何时触发（P4-02）。
4. **主体与权限**
   - 已定：Observer 不建事故（A8、P2-03）；web 已有建事故、Run 与事件的列权限。
   - 待决：
     - 消费执行者（推荐 web，P4-02）。
     - web 新增 release `UPDATE(incident_id)` 与新关联表 INSERT，并改守卫（P4-03）。
     - 若采纳 P4-01-A，Observer 新增对比表 INSERT。
5. **数据合同、迁移与部署顺序**
   - 待决：
     - 关联存储（P4-03）。
     - 输入 v6（P4-05）。
     - 迁移编号与对 PR-C 的依赖（P4-06）。
   - 部署顺序：先迁移；worker 必须先于或与 web 同时升级（旧 worker 读到 v6 会判 `INCOMPATIBLE_STATE`，`context.py:555-557`）；最后启用 web 的消费循环。
6. **旧数据与已归档证据**
   - 已定：
     - U2 校准归档与 ledger 不改写。
     - 旧事故不回填关联（F2 合同:33）。
     - v1–v5 照旧读取。
   - 注意：库里已有的 anomalous 且未关联的发布（开发库或测试库）上线后会被消费。这是合同意图，不需要回填。
   - 待决：PR-2 重放是否核对关联（R9）。
7. **并发与水位**
   - 已定：发布采样与清扫的锁顺序是 release→session；scope 挂起的锁顺序是 scope→incidents→releases（PR-2 §9）。
   - 待决：消费者的锁顺序（R2），以及与告警接入并发时的竞态口径（R2）。
8. **外部调用**
   - 已定：事故 Run 走现有 worker、模型与工具预算（每 Run 上限、F2 U6）。
   - 待决：Observer 的对比采集是否新增 Prometheus 查询，以及预算、超时和失败后的状态（P4-01）。
   - web 消费本身不发外部调用。
9. **验收投影与 `passes`**
   - 已定：PR-4 不翻 F11 `passes`（拆步:101-107，由 PR-5 翻）；F2 `passes` 排在 PR-4 之后（F2 U2-A）。
   - 待决：真实运行三场景的证据形态与前提（P4-07）。

## 6. 验收测试作者应覆盖的可观察行为（公开接口与 PG，不看实现）

1. 一个 anomalous 发布，目标上没有事故：一次 pass 后恰好得到 1 个新事故、1 个 queued Run。
   - Run 输入为 v6，含发布身份、前后版本、新实例证据，以及对比记录或 `unavailable`。
   - 发布的 `incident_id` 指向它；link 的 disposition 为 `created`。
   - 重复 pass、并发两个 pass、或事务失败后重试：都不产生第二个事故、Run 或 link，`replayed=True`。
2. 目标上有 1 个未关闭事故（含 resolved 与 observing_recovery）：只追加 1 条事件。
   - 事故的 `control_generation`、mode、lifecycle、当前 Run 都不变；不新建 Run。
   - 若当前 Run 正在运行，事件在下一个安全边界被纳入；若结论已发布，只记录。
   - disposition 为 `attached`。
3. 目标上只有已关闭事故：新建事故，`related_incident_id` 指向按 P4-04 选定的那一个，并开 Run；关闭的事故不被重新打开。
4. 多个开放事故：按 P4-04 的规则选出唯一一个；交接事故（target 为 NULL）不参与；其他目标的事故不参与。
5. 健康、unknown、cancelled 的发布与没有 ending 的发布：不产生任何事故、Run 或事件。连续健康发布不产生任何工作。
6. 目标无法解析或不一致：交接事故，无 Run，原因 `RELEASE_TARGET_UNRESOLVED`。
7. 权限负向测试：
   - Observer 与 worker 写不了 `incident_id`，也写不了 link 表。
   - web 无法把 `incident_id` 写到非 anomalous 的发布、已有关联的发布、或同一事务内没有 link 的发布上。
   - 发布的其余列仍然不可变。
8. 挂起期间：照样建事故与 queued Run；在挂起解除之前不发生任何查询或模型调用。
9. 续开 Run（追问、超时续开）保留 v6 发布事实；发布记录被篡改或缺失时判 `INCOMPATIBLE_STATE`。
10. 重放：篡改 link 的 ending、anomaly_key 或 incident_id 后，得到 `consistent=False` 与 `LINK_MISMATCH`。
11. 若采纳 P4-01-A：
    - 对比记录的 before 窗起止等于合同值。
    - 旧切片的 UID 集合恰好等于映射结果（多、少或外来实例都判不充分）。
    - 缺少 `before_pod_template_hash` 时只保留整体服务并给出原因码。
    - 采集全部失败时得到 `unavailable`，消费不会被永久卡住。
    - 对比不改变发布状态。
12. 零发布门写入：消费路径对 Kubernetes、CI 和流量策略不发任何调用（代码面与权限负向测试）。
