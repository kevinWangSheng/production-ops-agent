## 复用原则与候选路线

复用现有业务 demo、部署模板、遥测、SDK、故障场景、Agent baseline；保留来源和许可证，写清自己的修改。面试价值来自能解释与验证：为什么这样选、失败在哪、改动改善了什么、有什么成本。无需以从零写的代码比例为目标。

候选 A：发布事故调查与批准回滚。最完整但工程量最大，推荐作为长期叙事。

候选 B：只读事故调查与评测工作台。工具查询、证据、报告、实验比较、反馈闭环更快完整，推荐作为首次交付。

候选 C：给现有开源 SRE Agent 增加独立评测/可靠性改进。借用已有 baseline 加快起步，技术所有权通过改动与消融证明；上游依赖、理解成本和兼容性是代价。

推荐 B -> A；时间紧则 C。先完成完整纵向样例，再扩展平台能力。

## 第一条纵向链路

真实流量 -> 坏版本 -> SLI 告警 -> incident -> 只读查询 -> 证据报告 -> 有界动作建议 -> 人审 -> 独立 executor -> 持续恢复检查 -> 完整记录。

展示两种情形：发布确实导致故障，以及“刚发布但实际是下游变慢”。后者应该拒绝盲目回滚。仅展示固定坏版本会让规则脚本成为更合理方案，所以必须有规则基线和负例。

初版技术建议：Python 为主；单 Agent；持久化状态；显式只读工具；LangSmith 托管 tracing/eval；现有 Kubernetes rollout controller；独立进程/身份的 broker 与 verifier。工作流运行时只选一种。可先评估 LangGraph 持久化，不同时叠加 Temporal；[官方持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)。checkpoint 不自动证明外部动作幂等或 exactly-once，必须另测重试与副作用。

Go、多 Agent、OPA、L4、复杂 UI 暂缓到有实际需求时评审。身份隔离、确定性授权、独立恢复判断不能因为简化而丢掉。以上是建议，原验收要求未被修改或弱化。

## 完整 build/eval/operate 流程

1. 先明确业务与故障假设。选一个无状态服务、一条正常请求路径、一个允许回滚动作；确定 incident 成功/失败/弃权结果。
2. 建实验环境。先由确定性脚本发布坏版本、制造真实流量与告警，人工检查 telemetry 和恢复 oracle；场景真实成立后才接 Agent。
3. 建基线。规则 runbook、朴素固定工具 Agent、候选改进 Agent 使用同样数据、预算和可用权限；模型差异单独列出。
4. 建数据合同与最小用例集。输入中只放生产可见线索；故障标签与预期结果仅评测器可见。故障注入器、答案目录和专用标记不得成为调查工具的数据源。
5. 实现只读 Agent。每条事实带查询、窗口、时间戳与快照引用；明确证据不足、相反证据、工具超时和预算终止；从第一天记录 trace。
6. 离线 eval。固定证据回放便宜、适合诊断回归；相同场景/随机种子做配对比较。固定轨迹回放不能证明新工具策略和真实恢复效果。
7. Live eval。每次 reset、健康检查、开始流量、注入、运行、独立读最终状态、保存证据、清理。重新初始化数据和部署版本，避免上个实验污染下个实验。
8. 误差分析。按错服务、缺证据、错误归因、预算耗尽、错误动作、错误恢复分类；人工校准 LLM judge。只在开发集调工具与 prompt。
9. CI gate。每次变更跑确定性测试及小型固定回归；夜间/里程碑跑重复 live cases。记录模型、prompt、工具、策略、runbook、数据、部署、评测器版本；失败不能静默删除。
10. 人审执行与故障测试。批准绑定 incident/目标/版本/参数/过期时间；验证重复事件、worker crash、重试、过期审批、错误目标、provider 失败、缺失流量。
11. 持续运行。先 shadow/read-only；按计划注入低频故障，采样在线评分；72 小时只在后期执行。失败 trace -> 人工判定 -> 新开发/回归用例 -> 候选版本 -> held-out eval -> 发布或回退。
12. 求职交付。5 分钟视频、可复现实验命令、架构与边界、基线对比、一次明确改进、失败案例、资源与费用报告、借用/自写说明。

## Eval 如何可信

起步可用 6 类场景：真实坏发布、无关发布+下游慢、CrashLoop、缺 telemetry、重复事件/worker 重启、日志指令注入。每类逐步加入不同服务、负载、故障强度、噪声和种子。

按故障机制与变体分开开发集和保留测试集；不能只把同一模板随机分行。初步 30–50 个参数化实例仅是工程起点，不是统计充分性的保证。关键随机 Agent case 重复 3–5 次，发布每类分子/分母、重复次数、离散程度；零次违规不代表真实风险为零。已经用来调参的测试案例要重新分类并补新保留集。

确定性评分：目标资源、证据引用可解析性、动作权限、重复执行、final state、持续 SLI、流量存在性、时延、工具次数与成本。

人工/模型辅助评分：结论是否被证据支持、是否遗漏反证、报告可读性。使用细化 rubric 和证据；盲评模型身份；抽样人工标注校准 judge；争议人工裁决。不得由诊断 Agent 给自己的恢复结论打最终分。

业务指标包括定位正确率、证据支持率、应弃权时的弃权率、误回滚率、恢复率、首次有用证据耗时、单 incident 成本。完整分母与失败必须保留。真实环境恢复与固定证据诊断分别报告。

## 三种可观测性

- 服务状态：OpenTelemetry + metrics/logs/traces，回答用户是否受影响、哪个依赖异常、恢复是否真实。
- Agent 执行：LangSmith trace，记录模型调用、实际工具参数/结果、耗时、错误、token、费用、版本。记录可审计操作与结果，不要求隐藏思维链。
- Eval 质量：dataset example、experiment、repetition、evaluator version、score、人工反馈、CI artifact，回答新版本比基线哪里好、哪里坏。

用 incident_id / scenario_id / eval_run_id / trace_id 关联三层。外部审计和最终状态记录不依赖 LangSmith 成功上传；凭据和不应外传内容在上传前处理。

## 服务器与费用：估算，不是测量

不需要 GPU，先调用模型 API。主要 RAM/磁盘消耗来自 Kubernetes、业务应用、遥测存储和并行评测。缩短保留时间、限制流量与 eval 并行度。

- 本地起步：一台机器；建议可分配给容器 12–16 GB RAM、约 6–8 CPU、80–150 GB 空间，用精简服务和遥测。宿主机自身、IDE、浏览器另需资源。未验证最小值。
- 单台远程实验：8 vCPU / 16 GB RAM，约 100–200 GB 可用盘；精简栈且顺序实验。能证明进程故障与业务闭环，不能证明独立主机故障容忍。
- 推荐长期实验两台：A 为 Agent/持久化/调度，2–4 vCPU / 4–8 GB；B 为业务 K8s/遥测/注入，8 vCPU / 16 GB。A 与 B 分开故障域；A 可做外部流量/探测起点，但测量争用应监控。它们各自仍可能单点故障。
- 三台：仅需测试跨 worker 调度时，A 控制与评测、B/C workload worker；控制面位置明确，单控制面仍非 HA。若要证明 Kubernetes 控制面 HA，应单独设计 quorum 与故障域，不能把三个容器节点当三台独立服务器。

价格示例而非最便宜采购推荐：[DigitalOcean Regular Basic](https://www.digitalocean.com/pricing/droplets) 当前公开 2 vCPU/4 GiB $24/月、4 vCPU/8 GiB $48/月、8 vCPU/16 GiB $96/月。小 A+大 B 为 $120–144/月计算费。两个规格按公开小时价运行 72 小时约 $12.86–15.43；还需考虑备份、额外盘、税、网络、模型和观测费用。关机不等于释放计费资源，实验生命周期需按供应商计费规则设计。

模型费：N cases × R repeats × V variants ×（输入 token × 输入单价 + 输出 token × 输出单价）/1e6，再加 judge 和重试。建议先跑 10 个完整 incidents 测平均/p95 成本，才确定月预算；用 $30–100 作为初始支出上限建议，不是费用预测。

阶段性总预算建议：本地算力+$30–100 模型预算+观测费用；两台上述云规格则 $150–244/月再加观测与附加费用。最终按真实配置和实测 token 修订。

## 模拟真实性与资源验收

使用真实 HTTP 请求、真实错误/延迟、真实部署与 pods、真实 telemetry 和告警。故障参数可控，正常与异常数据都保留；Agent 看不到注入答案。独立探针验证 HTTP 正确性、流量量级和 SLI；不能只看 pod Ready 或错误率下降。

每个实验采集峰值/p95 CPU、RSS、磁盘增长、query latency、丢失 telemetry、Agent 成本；先顺序实验，再试两路并发决定是否加机器。业务故障与模型/工具/Agent 故障分别注入。单宿主机 kind 多节点仅模拟拓扑，不证明宿主机或可用区容灾。

## 时间与下一轮决策

以下是熟悉 Python/Docker、可复用上游且全职投入时的排期假设：第 1 周 lab 与 baseline；第 2 周只读 Agent+trace；第 3 周 eval+一次改进；第 4 周人审闭环；第 5–6 周恢复/持续运行/作品包装。Kubernetes 学习、复用兼容、兼职投入会增加周期。
