# 任务记录

任务记录遵循 [AGENTS.md 的任务记录与交接约定](../../AGENTS.md#任务记录)。
本目录保存需要跨会话或交接的任务及实验记录。

## 使用方式

- 使用稳定文件名，例如 `2026-09-08-dev-environment.md`。
  同一任务持续更新原文件，完成后原地保留。
- ROADMAP 链接当前任务，详细执行进展在任务记录中维护。
  简单修改无需建档，不适用的字段可以省略。
  待排的后续事项开 GitHub issue 并在记录里链接，不在记录里堆待办。
- 开始前填写目标、依据、前提、完成条件和下一步；
  执行后更新进展与证据。已有规范、计划和实验合同直接引用，不复制。
- 正文控制在两页以内：目标、状态、证据链接、待决。
  逐轮审查处置、命令输出等细节放 PR thread 或 `docs/evidence/`，记录只留链接与结论。
- 状态使用：待开始、进行中、阻塞、已完成、已取消。
  完成表示本任务的完成条件已满足；实验结论另记通过、失败或证据不足，
  不与任务状态混为一谈。

## 合同预审

非平凡功能与合同变更的每个实施步骤开工前做一次（按步做，后续步骤的细节在前一步落地后才看得清）；简单修改、纯文档、测试修复不做。

- 预审者：未参与实现的 Agent，只读。每条推荐先核对真实代码、配置与部署并引路径行号；没核对到的标「未确认」。2026-10-09 的教训：推荐「库层按角色分写权限」时没查 web 与 worker 共用 owner 角色，实施时才暴露。
- 必答类别，逐类给出「已定（引出处）」或列为待决：
  1. 时间：起点、时钟来源、容差。
  2. 计数与口径。
  3. 状态转移：由谁触发、何时触发、何时失效或陈旧。
  4. 主体与权限：对照真实部署的角色与凭据。
  5. 数据合同：存储位置、迁移、部署顺序。
  6. 旧数据与已归档证据的兼容。
  7. 并发与水位。
  8. 外部调用：模型或数据源、预算、超时、失败后的状态。
  9. 验收投影与 `passes` 的影响。
- 输出决定表，每行 `编号 | 问题 | 选项与代价 | 推荐 | 影响面 | 裁决`，分两组：需用户裁决（不可逆、合同、权限、验收）和可逆默认（Agent 自定，写一行理由）。
- 裁决后，决定表原样进任务记录的「合同」节，标修订号 `合同 r1`。实施中补的决定追加行并递增修订号。实现者报告就绪时写明对齐的修订号，与任务记录当前修订号一致才算就绪。
- 收尾在任务记录写四个数：实施期间新冒出的合同问题、因合同变更重写的测试、环境重跑次数、用户裁决轮数。

## 模板

```markdown

- 状态：待开始
- 更新日期：YYYY-MM-DD
- 依据：<相关计划、设计条款或验收要求的链接；适用时标注功能 ID>
- 工作区：<分支与 worktree 路径，开始执行时填写>

## 目标与范围

<要解决的问题、本次交付和范围界限>

## 前提与完成条件

- 前提：<依赖、必要环境、适用授权依据及缺失项>
- 完成条件：<可观察的结果、所需检查或审查；引用已有合同>

## 合同（r1）

<适用时：合同预审的决定表，裁决列已填；实施中补的行追加在后并递增修订号>

## 必要上下文

<相关文件、章节或参考实现的链接及用途>

## 执行进展与证据

<当前已完成和进行中的事项；重要失败与处置>

<每项验证记录：检查对象与版本、实际命令或步骤、
预期与实际结果、结论及证据位置；尚未执行的明确标注>

## 下一步与交接

<下一项具体动作；阻塞原因及解除条件；尚未验证事项>

<适用时记录运行中进程或服务及资源归属、未提交工作、
合并与 worktree 清理状态，以及清理后仍可访问的证据位置>
```

## 实验任务

实验执行前，在“前提与完成条件”中填写实验问题、版本、
步骤、预期结果、通过/失败判据、证据位置及失败处置；
已有实验合同直接链接。

执行结果记录在“执行进展与证据”。
