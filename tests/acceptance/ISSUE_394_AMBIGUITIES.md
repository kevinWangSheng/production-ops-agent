# Issue #394 ambiguities

Points the contract (rows A2, A5, B1, B9, B10, B11) and the #394 seams leave open. The tests do not enforce a choice on them unless stated.

1. Compose digest (deferred #392 test). B9/B11 want Compose to carry `image@sha256:<digest>`, but no digest exists before the user-gated first publish. The adapted test requires every product service to share one `${OPSPILOT_IMAGE:-opspilot:local}` reference and every non-product image (postgres) to be digest-pinned. The installer test enforces the digest for any non-local image. Still open: pinning Compose itself and the install record to the published digest after the first publish, plus `releases/<version>.json`.
2. Refusal wording. The installer refusal only has to exit non-zero with a message on stderr, before the secrets directory, install record or default config directory exists and before any docker build/pull/run/compose up. The message text is not checked.
3. Upgrade path. The seams say "install.sh refuses". The test also applies this to `upgrade` on an existing install: exit non-zero, secrets files unchanged, no build/pull/compose up. It does not check whether that refusal comes before `resolve_settings` re-applies `chmod 700` to the existing directory.
4. Digest accepted forms. "Ends in `@sha256:<64 hex>`" is read as accepting both `repo@sha256:…` and `repo:tag@sha256:…`, both tested with lowercase hex. Whether uppercase hex is accepted is not tested.
5. Image from `install.env`. A non-local undigested image that comes only from a persisted `install.env` (not from the environment) is not tested.
6. SemVer strictness. Tested as rejected: `1.2`, `1.2.3.4`, and a tag without the `v` prefix. Not tested: pre-release/build suffixes (`1.2.3-rc.1`) and leading zeros, because the seam says only `MAJOR.MINOR.PATCH`.
7. Checker problem text. `check()` must return a non-empty list of non-empty strings for each bad case. The tests do not check which wording names which problem.
8. How the CLI finds the repo. The CLI is run with `cwd` = repo root, as in the workflow. Whether it finds the repo from its own path or from the cwd is not checked. "Without the venv" is tested by running the base interpreter (`sys.base_prefix/bin/python3`) with `-I`.
9. Job layout. Ordering is checked only inside the single job holding `packages: write`: checkout (fetch-depth 0) and check_version before build; fetch origin main and is-ancestor before build; make setup, make check, QEMU and Buildx before build; a `GITHUB_STEP_SUMMARY` step mentioning the digest after build. The relative order of check_version, the ancestry check and make check is not enforced, and neither are other jobs in release.yml. Step names, summary wording and how the digest output is referenced are also open.
10. Job permissions. B10 says the job-level permissions are `contents: read, packages: write`. Because job-level permissions replace the workflow-level set, the test requires exactly that mapping on the publish job, plus workflow-level `{contents: read}` as in the seams.
11. `latest`. "Never `latest`" is checked as no `latest` word anywhere in release.yml outside comments and `runs-on:` lines. This also forbids a metadata-action flavor such as `latest=false`. If the implementer needs such a flavor, this is the assertion to revisit.
12. Token reference. Both `secrets.GITHUB_TOKEN` and `github.token` count as the repository token. No other `secrets.*` name may appear.
13. Not statically checkable. "No tag pushed, no image published" (issue acceptance) and real multi-arch builds stay with the reviewer and run evidence. The live docker test is opt-in (`OPSPILOT_394_IMAGE_LIVE=1`) and was not run.
