## 九类必答

1. **时间**

   已定：`released_at` 是发布源提交变更的时间，`received_at` 由 PostgreSQL `clock_timestamp()` 产生；`deadline_at = released_at + deadline_seconds`；未来时间拒绝，已过 deadline 的投递记录为 `unknown/late_delivery`，重放不重置时间（`docs/tasks/2026-10-12-f11-pr1-contract.md:60-61,97`；`opspilot/migrations/versions/0014_release_observations.py:62-82`）。

   PR-3 待决：载荷字段必须明确命名为 `released_at`，还是允许部署系统提供 `event_time` 后由适配器转换。推荐只接受 `released_at`，避免多个时间字段竞争。

2. **计数与口径**

   已定：同一 `(source, source_release_id)` 是一个发布主体；同键相同语义指纹为 replay，不增加主体；不同内容返回 `RELEASE_IDENTITY_CONFLICT`（`docs/tasks/2026-10-12-f11-pr1-contract.md:61,99`；`opspilot/migrations/versions/0014_release_observations.py:88-93`）。

   已定：采样预算属于发布主体，授权后的有效连续覆盖、健康窗口、deadline 和累计样本共同决定终态；合法 `unknown` 也计数（`docs/tasks/2026-10-13-f11-pr2-contract.md:885`）。

   PR-3 待决：一次 webhook group 是否允许多个发布事件。推荐一个 HTTP 请求只承载一个发布事件；批量发送由 harness 逐个发送，避免部分成功语义。

3. **状态转移**

   已定：`pending → observing → healthy | anomalous | unknown | cancelled`，终态不能由旧采样重开（`docs/tasks/2026-10-12-f11-post-release.md:27-37`）。

   已定：发布 webhook 只负责登记；授权由 web Controller 在同一授权事务中完成，授权只匹配冻结 policy 清单；清单为空返回 `RELEASE_POLICY_UNCALIBRATED`（`docs/tasks/2026-10-13-f11-pr2-contract.md:880-884`；`opspilot/observation/release_policy.py:142-155`）。

   已定：当前发布会话必须显式使用 `purpose='release_observation'`、`subject_kind='release_observation'` 和 `subject_id=release_observation_id`（`opspilot/migrations/versions/0015_release_observation_sessions.py:45-66`）。

4. **主体与权限**

   待决：发布 webhook 是否只接受专用 actor。推荐专用 `release-deployer` actor；Alertmanager actor 不能提交发布。配置仍复用 `OPSPILOT_EVENT_TOKENS` 的 `<sha256>=<actor>` 格式（`opspilot/web/__main__.py:175-180`；`scripts/kind_lab.py:462-475`）。

   已定：产品不持 Kubernetes 凭据；harness 才能执行实验发布。产品角色通过 PostgreSQL 权限登记发布，现有 web grant 允许发布表列级 INSERT（`opspilot/migrations/versions/0014_release_observations.py:145-147`）。

   PR-3 必须新增路由级 actor 守卫，不能只复用通用 `event_channel`。

5. **数据合同、迁移、部署顺序**

   已定：发布表迁移为 `0014`，发布 session/subject 迁移为 `0015`，后续 deadline evidence 为 `0016`（`opspilot/migrations/versions/0014_release_observations.py:7-10`；`opspilot/migrations/versions/0015_release_observation_sessions.py:7-10`）。

   已定：发布主体和投递审计列已有约束：source/id、版本摘要、`released_at`、`received_at`、deadline、raw/semantic hash、16 KiB 审计文本限制（`opspilot/migrations/versions/0014_release_observations.py:49-113`）。

   部署顺序：停止 web、worker、Observer，执行迁移并检查 head，再启动；PR-3 不应新增独立 schema 分支。具体顺序依据 `docs/development.md:30-35`，当前部署脚本未核对到自动执行 PR-3 迁移，标记为**未确认**。

6. **旧数据与已归档证据兼容**

   PR-3 不应修改旧 incident HTTP 入口、F6 replay 或旧归档格式。

7. **并发与水位**

   已定：发布主体唯一索引由数据库裁决；投递审计按主体 sequence 递增，存储层使用 advisory lock（`opspilot/migrations/versions/0014_release_observations.py:88-113`；`opspilot/observation/releases.py:445-467`）。

   已定：发布采样锁顺序是 release → session；授权/控制还要先锁 scope，再锁 release、session（`docs/tasks/2026-10-12-f11-post-release.md:46`；`docs/tasks/2026-10-13-f11-pr2-contract.md:688`）。

   PR-3 待决：同一发布的并发 webhook、harness 重试和请求超时如何返回。推荐依赖 `(source, source_release_id)` 幂等键：首投提交后重试返回 200 replay；事务失败返回 503，调用方可重试；身份冲突返回 409。

8. **外部调用**

   已定：发布接收本身只调用 PostgreSQL，不调用模型或 Prometheus；采样由后续 Observer 完成。harness 当前 `publish()` 通过 `kubectl patch deployment` 改 checkout 环境变量，记录 patch 成功后的时间为 `released_at`（`scripts/f11_u2_harness.py:1217-1258`）。

   已定：当前 HTTP body 通用上限为 64 KiB，Alertmanager 专用上限为 1 MiB（`opspilot/web/app.py:51-54,206-210`）。PR-3 应设置独立 release body 上限，不继承 1 MiB。

   待决：失败是否让 harness 自动重试。推荐仅对 503/网络失败重试；400/401/403/409/422 立即失败并保留 ledger。

9. **验收投影与 `passes` 影响**

   已定：数据库保留 `anomalous`，UI/验收投影为 `degraded`；`unknown` 保持 `unknown`（`docs/tasks/2026-10-12-f11-post-release.md:31-37`）。

   已定：F11 `passes` 只有四步真实证据齐全后才能改为 `true`，当前仍为 `false`（`docs/tasks/2026-10-12-f11-post-release.md:20-21`；`feature_list.json:108-119`）。

   PR-3 即使 webhook 登记和 harness 发布成功，也不能翻 `passes`。当前 policy 清单为空时，真实运行只能取证：认证、载荷规范化、目标解析、登记、幂等、零查询；授权会明确返回 `RELEASE_POLICY_UNCALIBRATED`，不能伪造完整观察成功。

## 验收测试作者应覆盖的可观察行为

按 `IncidentScenario -> IncidentOutcome` 或公开接口描述：

1. 合法专用 actor + 合法 payload → `201 created`，一条 release observation、一条 delivery audit，状态 `pending`。
2. Alertmanager actor 或其他 event actor → `403 RELEASE_ACTOR_REQUIRED`，无 release observation、无查询、无事故。
3. 缺 `source_release_id`、缺 `released_at`、无时区、版本摘要非法、未知业务字段 → `400`，不写主体。
4. 未知字段进入脱敏限长审计，不进入语义 hash、target、版本或查询范围。
5. registry 无匹配目标 → `422 TARGET_UNRESOLVED`；多条匹配 → `422 TARGET_AMBIGUOUS`；字段不符 → `422 TARGET_MISMATCH`；三者都不建主体、不发查询。
6. `released_at` 晚于 DB 接收时间 → `422 RELEASE_TIME_IN_FUTURE`。
7. 首次投递已过 deadline → 成功记录审计和主体，状态 `unknown`、原因 `late_delivery`，不创建 session/task。
8. 同 `(source, source_release_id)` 相同语义重放 → `200 replayed`，不改变主体、时间、policy 或 sequence 语义。
9. 同键不同 target、版本或时间 → `409 RELEASE_IDENTITY_CONFLICT`，原记录不变。
10. PostgreSQL 写入失败/锁超时 → `503`，无半个主体；可安全重试。
11. webhook 成功登记后授权，policy 清单为空 → `RELEASE_POLICY_UNCALIBRATED`，无 session/task。
12. harness patch 改变 checkout 模板并记录 before/after digest、ReplicaSet UID、Deployment generation、`released_at`。
13. harness 通过真实 HTTP 发送 webhook；响应、actor、raw/semantic hash 与 ledger 可互相核对。
14. harness 自身 patch 造成的 rollout 变化被标为实验动作；产品 webhook、授权、Observer 路径未写 CI、部署门、rollout 或 traffic policy。
15. 旧 incident intake、旧 incident replay、旧归档证据行为保持原结果。
16. 所有 PR-3 证据完成前，F11 `passes` 仍为 `false`。

## 是否需要 kind 真实运行

需要。PR-3 合同明确要求真实 kind 环境；仅单元测试或本地 mock 不能证明：

- 专用 actor/token 在真实工作台部署中的绑定；
- harness 能改变应用镜像或配置且不重建 chart；
- webhook 从 harness 到工作台的真实传输；
- before/after digest、ReplicaSet、Deployment generation 与 `released_at` 的一致性；
- 产品路径没有写 CI、发布门、rollout 或 traffic policy；
- policy 清单为空时真实返回 `RELEASE_POLICY_UNCALIBRATED`，且无查询、无事故、无授权 session。

最低证据：

- 冻结 harness 与产品代码 revision/hash；
- webhook 请求/响应、actor、HTTP 状态、raw/semantic hash；
- kind 中 patch 前后 Deployment/ReplicaSet/Pod 快照；
- PostgreSQL release observation/event 查询结果；
- policy 为空时的拒绝结果；
- 零发布门三层证明：代码断言、权限负向测试、harness 发布前后实际策略快照；
- `summary.json` 及其 sha256；不把原始 ledger 入库。

正式 healthy/degraded/unknown 观察和 F11 `passes=true` 必须等待 policy PR 写入批准的校准项后再做。
