# 版本计划对抗性审查

日期：2026-09-06。按用户要求由独立 subagent `version_plan_review` 审查；父 Agent 对照现有规格核查并记录处理意见。文档审查，不包含实现、运行或效果验证。

## 被审方案

会话提议：V0 上游基线与设计验证；V1 完整发布关联事故调查产品；V1.1 运行反馈改进；V2 扩展非发布事故或服务形态；V1 作为项目完成目标。该方案尚未写入正式 ROADMAP。

## 独立审查结论

原版本计划不宜直接采用。产品方向成立，但版本划分混杂，首版范围收缩未经验证。建议使用“一个完整产品交付目标＋内部工程里程碑＋未承诺的候选扩展”。

### 1. 高：非发布事故整体推到 V2，可能改变已确认完成范围

SPEC.md:11、15–16 将告警与发布作为两个并列入口；PRD.md:85 要求完整 incident/post-release workflow。将 V1 作为完成目标、非发布事故作为 V2，会使无近期发布的告警调查缺席。

反例：无发布时的下游超时，与恰逢发布时的下游超时，调查工具和证据需求高度重合。是否存在发布事件不是合理的整版划分依据。可以限定事故家族，但不应未经分析移走一个入口。

### 2. 高：首条开发案例的合理性不等于首版范围的合理性

“发布关联起点明确、可验证”只能支持候选贯通案例。SPEC.md:83–89 与 ROADMAP.md:14–18 明确能力映射、支持矩阵和环境仍待分析。

发布前后对比还需要版本维度遥测、正常流量、基线窗口和部署历史，未必比一般依赖故障更省成本。应对证据可得性、上游覆盖、场景价值和验证成本做比较。

### 3. 中高：V1 只有最终验收包，缺少可执行的中间结果

完整性要求本身正确（SPEC.md:20、48–50、73–79），不能以范围大为由删除安全和可靠性。但一个版本名装下全部工作，没有说明如何逐步获得运行反馈。ROADMAP.md:23–28 已有工程顺序，并强调安全/观测/交付从首个可运行系统适用。

### 4. 中：版本单位混用，反馈时间表容易误导

V0 是研究阶段；V1 是产品交付；V1.1 是贯穿开发运营的修复活动；V2 是未确定扩展。编号本身无错，但当前混合了不同维度。“V1.1 再改进”可能只是表述问题，仍需明确反馈修复贯穿每个里程碑。

### 5. 中：“复盘草稿”漏写审核与受控知识沉淀

SPEC.md:19、44 和 PRD.md:67–69 要求人工确认、来源与知识审核闭环。仅写草稿可能使实现漏掉既定能力。应补回，而不是增加自动自学习平台。

### 6. 中：完成条件尚未落成可执行门槛

SPEC.md:75 仍待冻结质量、费用、资源和时延目标。持续运行时长不能独立证明效果。支持矩阵、独立判定、质量/成本预算与故障验收须随基线证据明确，不能凭版本名宣布规划已可实施。

## 成立的部分

有限支持范围、真实软件验证、发布无关反例、完整交付要求、保留只读边界均成立。基线和扩展也应保留，只是不应混用为同一级产品版本。

## 父 Agent 处理意见

接受上述六项发现。第 4、5 项含表述遗漏风险，不能说此前明确打算推迟所有反馈或删除知识审核；但必须纠正歧义。撤回会话中 V0/V1/V1.1/V2 分版建议，不改动已确认产品边界或验收要求。

产品交付目标保持一个：在待明确的有限支持矩阵内，覆盖告警与发布两个入口，以及调查、跟踪、人工交接/处置记录、独立恢复观察、复盘审核、可靠交付与运营。

建议的工程规划表达，待能力映射后具体化并与现有 ROADMAP 对齐：

1. 设计与上游基线验证：比较支持场景、证据与成本，确定复用及验收；不是产品版本。
2. 首条完整可运行流程：用代表案例贯通调查到审核复盘，带基础权限、状态、观测与重复部署；是内部中间状态，不作为完整产品交付。
3. 完成支持矩阵与故障行为：覆盖两个入口、反例、缺信息、重复事件、重启/取消和持续跟踪；每阶段均处理运行反馈。
4. 完整发布验收：按照预先审定的支持声明和检查执行 held-out、故障注入、持续运行、升级/恢复，报告效果与限制。

未来扩展留作候选，不预先命名或承诺 V2。第一条实现案例尚未确定为发布回归；正式发布号在发布内容明确后再定。

下一步仍是上游能力映射和候选支持矩阵比较，而不是请求用户批准另一套未经验证的版本号。本次不清除实施评审门禁。
