## Purpose

Build an effective, continuously running read-only operations investigation Agent to demonstrate complete Agent engineering for a job-search portfolio. Real-software simulated environments support this goal; operating an unrelated personal application is not a prerequisite.

The two entry points are incident alerts and observed releases. Both use the same investigation, evidence, incident state and human interaction capabilities. The product provides investigation and advisory findings, not authority over production releases.

## Confirmed scope

- Incident investigation: receive alerts, correlate signals, resolve exact targets, actively query permitted sources, test competing hypotheses and report evidence-supported findings or explicit uncertainty.
- Post-release investigation: observe before/after revisions, compare service behavior and follow delayed regressions. Results are advisory and cannot approve, block, promote or revert releases.
- Ongoing follow-up: update the same incident as evidence changes, avoid duplicate investigations, support pause/cancel/takeover/close/reopen, and preserve human corrections against late task completions.
- Recovery observation: after a human independently handles an incident, use read-only service evidence and a sustained window to report recovery, continued degradation or unknown state.
- Postmortems: draft an impact summary, timeline, findings, uncertainty, human handling and recovery evidence; reusable knowledge requires human confirmation and provenance.
- Full engineering lifecycle: integration, secure tooling, reliable runtime, interaction, software tests, evaluation, deployment, upgrades, recovery, observability, budgets, sustained operation and verified improvements.

## First complete release — capabilities and evidence

The complete release includes both incident and post-release entry points and all active PRD/acceptance features. It accepts an investigation request and available context, acquires additional evidence through authorized tools, updates findings, supports human interaction, observes recovery and produces reviewed postmortems. It must not require a caller to select a predefined fault family.

Product capability boundaries are connected environments/data sources, exact target identity, supported query interfaces, permissions, available context and operational budgets. A new symptom within that boundary is not rejected solely because it is absent from the test catalog. ## Model priority and design ownership

Confirmed user priority on 2026-09-07: adapt the first implementation to DeepSeek. Keep a replaceable model boundary for future GLM or other providers; this does not require implementing those providers in the first release. User decision on 2026-09-09: use Flash by default and call its explicit alias rather than relying on Pro rerouting. **User decision on 2026-09-15: switch the outbound request name to `deepseek-flash`.** The vendor changelog of 2026-09-10 states that V4 Flash is *retired* and that `deepseek-v4-flash` is only *temporarily routed* to V4.1 Flash; the pricing page adds that the legacy names are *still accepted, but the corresponding models have been retired, their requests are served by the DeepSeek-V4.1-Flash model*. The legacy name therefore still works today but carries an undated expiry, while `deepseek-flash` is the documented name for the current model and the only Flash id listed by the official pricing page and the models endpoint as checked on 2026-09-15 (the repository's own `/models` artifact is the 2026-09-10T02:28Z snapshot; no new call to that endpoint was made).

This changes the requested name, not the serving backend — but that statement rests on the vendor documentation above, **not** on per-run identity records, and must not be read as a verified property of the frozen calibration set. What the repository actually establishes: the recorded response-name boundary lies in the roughly nine-hour window between `flash-results.json` (`ended` 2026-09-09T17:18:01Z, reporting `deepseek-v4-flash`) and `m002-saved-report-02` (2026-09-10T02:26:34Z, reporting `deepseek-flash`); the first calibration run `m002-saved-report-01` begins at 2026-09-10T02:19:02Z, i.e. **at** that boundary rather than after it, and its response was not preserved because identity verification failed (`round-02-provider-identity-decision.md`). Of the eight M002 per-run records, three carry a reported name, one is the unpreserved response, and the four investigation runs record no model identity at all. No record in M002–M004 reports `deepseek-v4-flash`.

Recalibration is therefore not required — today's `deepseek-flash` reaches the same backend that served the legacy name during calibration — but the basis is the vendor's retirement notice, not per-run identity coverage. The current validation profile is therefore DeepSeek official Chat Completions-compatible service, `deepseek-flash`, thinking/high; its availability and exact dependency/protocol compatibility require M0 verification and recorded versions. The response check is exact-match fail-closed: with `deepseek-flash` requested, a reply reporting the retired `deepseek-v4-flash` is rejected.

**Caveat — the new name is a floating alias.** The changelog defines `deepseek-flash` as *the latest V4.1 Flash model*, so the reported string stays constant across a future generation change. Exact matching therefore became stricter but *less discriminating*: it can no longer detect the backend swap that the retired fixed name would have surfaced as a changed string, and the profile records this weaker guarantee as `version_scope: "floating_alias"`. Detecting generation drift now requires a separate signal, not the name check. **This is a precondition, not an advisory:** before any run is compared against the frozen calibration, backend identity must be established by a `/models` metadata check — the mechanism already exists in the repository as the pinned `provider_models_response_sha256`. This is **enforced at the contract layer**: an approval contract must declare `models_metadata_sha256` — the digest of the official `/models` snapshot it was approved against — and a missing or malformed value is denied before claim; `claim()` writes it to a readable `m0_live_once.models_metadata_sha256` column so the approved snapshot can be checked against the calibration-era one afterwards (the contract hash alone only proves it was not tampered with, it cannot be read back). What remains open is **freshness**: without an extra request the runtime cannot prove the declared digest is current, so that step stays with the approver. This matters for the frozen B2 calibration, whose purpose is precisely to notice such drift.

Approved implementation approach: shared investigation instructions and output/evidence contracts; provider/model-version capability configuration for protocol differences; minimal prompt adjustments only when official requirements or controlled evaluation justify them. Do not fork a complete investigation prompt or workflow for every vendor by default. Record effective prompt, adapter, model, endpoint/mode and tool-schema versions per run.

The layering, how each revision is minted and what forces a bump are defined in the approved technical plan (sections 5 and 8). The writing rules derived from the current model's own characteristics are in [the DeepSeek V4.1 Flash reference](docs/design/deepseek-flash-prompt-tool-reference.md), which is date-bound and re-checked when the vendor changes. **Read both before writing any prompt or tool description.** See `docs/research/model-adaptation-and-design-ownership-2026-09-07.md` for current evidence and responsibilities.
