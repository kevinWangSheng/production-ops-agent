## 目标与范围

告警重复与部署事件按声明的策略关联而不吞掉不同的并发事故；worker 被杀后同一事故用保留的证据恢复、重复工作有界；单个查询卡住时有整请求时限并清理；告警风暴下有优先级、并发上限与背压；在途取消或暂停时迟到完成不覆盖人工决定。现状差距见合同第二节：步骤 5 大部分已证明，步骤 2 只有替身测试，步骤 1、3 部分，步骤 4 缺失。

不在范围：跨 Run 的事故累计预算、子进程隔离、工具并行、Prometheus 以外数据源、按时间窗或资源名合并告警。

## 合同（r1）

完整决定表见 [2026-10-17-f2-contract.md](2026-10-17-f2-contract.md)。用户 2026-10-17 对 U1–U9 全部按推荐裁决，可逆默认 R1–R8 按表执行。

- U1-A：同来源、同 fingerprint、同精确目标再 firing（新 `startsAt`）且旧事故未 closed，追加为事件（投递结果 `attached`，不开第二个 Run）；旧事故已 closed 则开新事故并写 `related_incident_id`；不同 fingerprint 各自成事故。
- U2-A：部署事件经 F11 PR-3/PR-4 进入，F2 `passes` 排在 F11 PR-4 之后；附带裁决 F11 U8 = 目标已有开放事故时追加发布证据事件并写关联，不开第二个调查，不覆盖人工控制。
- U3-A：查询超时记 `timeout`、`source_contact=possible`，作为工具错误回模型，模型在每 Run 上限内自行决定重查；不加网关自动重试；Run 层失败按 ADR-0005 交接。
- U4-A：照常接收并建事故与 Run；排队 Run 超过 `OPSPILOT_BACKLOG_MAX`（默认 8）时，最低优先级的停放为 `waiting_human`，原因 `BACKLOG_FULL`，人工 `follow_up` 重新排队。
- U5-A：优先级取告警 `severity` 标签固定映射（critical > warning > 其他），同级按 deadline，只影响领取顺序；风暴运行：PG 确定性测试约 50 条，真实运行 12 条合成 webhook、容量 2、积压上限 6，真实模型 + fixture 工具档。
- U6-A：每事故预算 = 每事故同时一个当前 Run × 每 Run 上限；追问新 Run 各自一份。
- U7：三个断点各一次真实 `kill -9`；每次 kill 后重发模型请求 ≤ 1、重派查询 ≤ 1，已提交证据全部保留，新 epoch 在租约到期 + 一个轮询周期内开始。
- U8-A：#242 压缩取证与步骤 2 同组真实 Run 取证，单独断言，不作为 `passes` 门槛。
- U9：五步确定性测试全绿 + 一次 kind 串行会话（步骤 1、2、3、5）+ 步骤 4 非 kind 真实风暴；步骤 5 可引用 `f7-step4-live`、`f12-live`，只补事故级 pause/cancel。
- R1–R8：线程 + 关 socket 实现整请求时限；卡住响应字节丢弃；每 worker 容量 `OPSPILOT_WORKER_CAPACITY`（默认 2）；优先级列由 0018 或基于 0018 的 0019 加入；advisory 锁键改为 `fingerprint+target`；追加事件只放白名单字段；宿主侧慢滴代理注入卡住；风暴用合成 webhook 直投。
