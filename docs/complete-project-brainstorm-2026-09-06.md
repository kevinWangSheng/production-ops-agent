## 最新目标与讨论边界

用户明确：主目标是做 Agent，使其真实运行并达到效果。模拟业务、开源系统、服务器、评测和观测均为此服务。本轮先决定是否值得做，以及从设计到持续运行的完整流程、必须解决的问题；具体工作负载、服务器和实现选型后续再谈。

上一版偏向个人应用运营，之前一版偏向 demo/eval 局部，均偏离主线。当前文档取代这些推荐。`docs/research/long-running-workloads-2026-09-06.md` 仅保留为后续环境候选资料，不要求用户真实使用任何个人应用，不把运营照片库/博客作为项目目标。模拟真实环境是可接受且必要的验证方式。

完整性：在明确能力边界内完成产品、软件交付与持续运营全生命周期。能力可以停在只读调查，但其稳定性、实际帮助、故障处理、权限、可维护性和反馈闭环必须完整。按生产标准设计和验收，不等于在没有生产证据时声称 production-proven。

## 立项判断

建议做。该领域具备 Agent 的合理任务：面对不完整、跨系统且不断变化的证据，动态选择查询、验证/否定假设，向操作者提供可检查的定位与下一步。这些能力可以在运行中的真实软件栈里检验，并直接展示 Agent 工程、后端与可靠性工程能力。求职项目无须依赖新商业类别或原创框架，复用是合理路径。

成功不以接入多少组件或写了多少代码衡量，而以三方面衡量：调查是否有实际帮助；运行时是否可信；能否持续维护和改进。若最终无法比规则/既有调查工具提供额外帮助，或成本与维护负担明显超过效果，应如实回到能力设计，而不是扩大 UI 和依赖掩盖问题。

范围建议：一个部署体系、明确的服务/事故支持矩阵、一组有限数据源；自动触发到持续调查、证据化结论、人工交接、状态复查和事故归档完整闭合。Agent 是否执行生产写操作作为单独边界决策；只读可成为最终产品边界，不是半成品。当前尚未由用户选定读写终点。

## 必须覆盖的完整流程和关键问题

### 1. 定义效果、支持边界与责任

明确服务对象、典型事件、Agent 输出如何改变人工下一步；界定支持/不支持的环境、数据和故障；定义调查完成、继续、弃权、超时、升级人工、关闭/重开条件。效果指标与运行SLO、成本上限在实验前确定。只读约束针对被运维环境，Agent 本身的状态/报告仍需持久化。

关键问题：Agent 到底负责哪一段；何时有足够证据；何时交接；是否在正常状态制造额外告警；如何防止范围外问题被自信判定。

### 2. 建立可复用接入和环境上下文

接事件、metrics/logs/traces、变更、服务依赖、身份、版本与 runbook；处理资源映射、时间范围、数据新鲜度、缺测、权限和上下文更新。调查器必须能迁移到另一个实例或新版本，不能将答案写死在服务名/日志样例里。

关键问题：证据在哪里、属于谁、能不能查询、是否已过期、是否跨源一致；新服务或新版本如何接入；没有现成 trace 的应用如何补足必要证据。

### 3. 设计并实现调查能力

决定如何复用既有调查内核与工具；模型依据；查询规划；支持/反证；工具预算；上下文裁剪；阶段性摘要；组织知识和历史事故使用；何时停止。工具要有明确 schema、返回量/超时约束、错误分类和可追溯来源。

关键问题：能否主动获取缺少的信息；是否把相关性当因果；是否围绕错误假设反复查询；压缩是否丢关键证据；知识陈旧如何处理；何种步骤适合规则而非LLM；模型质量/成本/延迟如何取舍。

### 4. 实现可靠的服务运行时

事件到持久 incident；队列、去重、并发、任务状态、checkpoint、重启恢复；超时与有界重试；provider/tool 故障降级；取消、预算、背压、卡住任务检测。对外部副作用另行验证幂等，持久化并不自动等于 exactly-once。

关键问题：进程被杀后任务是否丢；同一告警是否反复调查；故障风暴是否积压无界；模型不可用时是否静默失败；长期调查如何更新而非全部重做。

### 5. 强制权限、安全和资源边界

最小权限读身份、凭据隔离、查询范围/速率约束；hostile logs/runbooks/tool output；环境与incident身份；审计、数据脱敏、隔离。若包含动作，增加外置授权、具体审批、确定性执行和独立恢复验证。

关键问题：自然语言能否扩大权限；日志里的指令能否变成操作；只读查询能否压垮后端；模型请求/trace 是否携带凭据；不同环境和事故数据是否混淆。

### 6. 完成人机工作流

提供用户能实际使用的 API/界面：触发、查看进度与证据、追问、补充事实、纠正、取消、接管、关闭和重开。输出包含影响、时间线、结论/假设、证据/反证、缺口和下一步。人处理后 Agent 可继续只读复查状态并保留处置结果。

关键问题：报告是否帮助采取下一步；人能否快速核对；调查失败是否被明确呈现；反馈会不会丢失；同一incident多轮交互是否一致。

### 7. 验证功能、实际效果及失效行为

单元、接口、集成、端到端；权限与异常；真实软件上的正常/异常负载、部署变化、缺测和运行时故障；离线/live eval 与基线。将故障注入真值和答案隔离于Agent；区分已知/保留场景，重复非确定运行。

关键问题：真实证据能否支持结论；是否只记住测试模板；未知问题能否合理降级；人工核对成本是否抵消帮助；服务宕机和模型宕机能否区别。数值指标包括首次有用证据、定位/证据支持、错误/漏报/合理弃权、成本、时延与任务完成/恢复，不仅一个成功率。

### 8. 形成可重复的软件交付

源码/配置/依赖与镜像版本；代码评审和CI；可复建部署；staging；版本兼容；发布检查；分批上线与回退；数据和运行状态备份恢复。模型、prompt、工具和知识变更也必须版本化，并接受相应质量门槛。

关键问题：本地通过能否线上运行；升级是否破坏在途任务；回退是否兼容状态schema；环境重建是否靠人工记忆；上游变化如何吸收而不破坏能力。

### 9. 运行可观测性、运营与排障

业务事实、Agent调用/工具轨迹、任务/队列/错误、质量反馈、资源与费用，用统一incident/run/version标识关联；外部探测Agent失活；告警、值守手册、容量与retention、供应商配额、升级维护与故障处理。

关键问题：Agent不工作时谁发现；工具慢还是模型慢；日志/证据是否缺失；费用为何上涨；是否能从事故记录还原问题；什么情况下限流、降级、回退或停用。LangSmith属于这个系统的一部分，不替代整个运行与维护流程。

### 10. 持续改进及完成验收

运行问题 -> 证据 -> 定位 -> 修改代码/工具/上下文/告警 -> 回归 -> 发布 -> 持续观察。每个问题保留初始失败、原因、修复和验证；范围内阻断问题必须闭合，范围外问题进入待评审记录。

关键问题：修复是否真的改善；是否引入回归；错误知识是否被再次使用；是否只优化平均值而恶化尾部；上游升级和业务变化后是否仍有效。

## 模拟环境的定位（具体方案后续）

选择少量真实开源软件，实际运行进程、依赖、持久数据、业务请求和版本变化；正常背景负载持续存在。在可控隔离环境引入资源/依赖/配置/发布等问题，补充未见变体；同一环境经历长时间运行而非仅预制输入输出。必要时选第二种拓扑验证接入泛化。

环境服务于Agent质量与可靠性验证，不要求用户运营另一个个人产品、不要求真实客户流量，也不把随机等自然事故作为计划。模拟流量/注入与真实生产证据分别标记。完整业务选择、容量与云资源方案在本轮范围确定后详谈。

## 完成与停止边界建议

在支持范围内满足以下才算本项目完整：

1. 自动触发、持续调查、证据输出、人工交接、状态跟踪和归档全部可运行。
2. 在有正常背景活动的真实软件栈上，对正常/故障/缺信息/新变体有明确效果与失败证据。
3. 任务重启恢复、依赖中断、重复事件、负载与预算验证通过；不静默丢任务或无限循环。
4. 权限由系统强制，证据可追溯，人可以接管；若有动作，独立授权与验证完整。
5. 能可重复部署、升级、回退、备份恢复，且有操作说明与运行监控。
6. 持续运行、经历版本变化与故障处理，并发布实际质量/成本/可靠性结果；时间窗口与数值门槛需在实施前定，不把运行若干小时单独当证明。
7. 出现的范围内阻断问题已修复并回归，已知限制如实记录。

达到上述后可停止能力扩展；自动写、多集群、多租户等是否纳入由支持范围决定，不是自动追加的完整性要求。
